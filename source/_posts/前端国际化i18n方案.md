## 翻译文字只是国际化的一部分

把中文字符串替换成英文字符串并不等于完成国际化。日期到底按用户时区还是业务时区显示、价格使用哪种货币、阿拉伯语是否需要从右到左排版、复数如何变化，都会影响用户是否真正看懂页面。

先定义语言来源和优先级：URL、账户偏好、浏览器语言和默认语言谁优先。服务端渲染的项目还要让服务端和浏览器在首屏使用同一语言，否则会出现内容闪烁或 hydration 不一致。

## 选择库时先看应用边界

Vue 应用通常选择 `vue-i18n`，它与 Vue 的响应式和模板集成较好。需要在 React、Node.js、原生页面或多个框架间共享翻译资源时，`i18next` 的跨运行时生态更合适。两者都不会替你解决翻译流程、术语一致性或时区决策。

无论使用哪一个库，翻译键应表达稳定的业务含义，例如 `checkout.submit`，不要直接拿中文文案当键，也不要让同一个键在不同页面表示不同意思。

## 用 Composition API 配置 vue-i18n

下面的配置显式启用 Composition API，并把消息、数字和日期格式分开。项目可以按域拆分语言包，避免把一个巨大对象塞进首屏。

```ts
// src/i18n/index.ts
import { createI18n } from 'vue-i18n'
import zhCN from './locales/zh-CN.json'
import enUS from './locales/en-US.json'

export const i18n = createI18n({
  legacy: false,
  locale: 'zh-CN',
  fallbackLocale: 'en-US',
  messages: {
    'zh-CN': zhCN,
    'en-US': enUS,
  },
  numberFormats: {
    'zh-CN': {
      currency: { style: 'currency', currency: 'CNY' },
    },
    'en-US': {
      currency: { style: 'currency', currency: 'USD' },
    },
  },
  datetimeFormats: {
    'zh-CN': {
      short: { year: 'numeric', month: 'long', day: 'numeric' },
    },
    'en-US': {
      short: { year: 'numeric', month: 'short', day: 'numeric' },
    },
  },
})
```

在组件中使用 `t`、`n` 和 `d`，不要自己拼接货币符号或日期顺序：

```vue
<script setup lang="ts">
import { ref } from 'vue'
import { useI18n } from 'vue-i18n'

const { d, n, t } = useI18n({ useScope: 'global' })
const cartCount = ref(3)
</script>

<template>
  <p>{{ t('cart.items', cartCount) }}</p>
  <p>{{ n(1234.56, 'currency') }}</p>
  <p>{{ d(new Date(), 'short') }}</p>
</template>
```

英文复数可以在翻译资源中定义多个形式，中文资源通常只使用一个带 `{count}` 的形式。复杂语言不要假设“单数和复数”足够，必要时根据目标语言增加复数规则并请母语者审校。

## 语言切换需要验证和加载边界

不要直接把 `localStorage` 里的任意值交给 i18n。语言列表必须是白名单；动态加载也应使用显式映射，让构建工具能分析依赖。

```ts
// src/i18n/locale.ts
import { i18n } from './index'

const loaders = {
  'zh-CN': () => import('./locales/zh-CN.json'),
  'en-US': () => import('./locales/en-US.json'),
} as const

type Locale = keyof typeof loaders

export async function setLocale(target: Locale) {
  if (!i18n.global.availableLocales.includes(target)) {
    const module = await loaders[target]()
    i18n.global.setLocaleMessage(target, module.default)
  }

  i18n.global.locale.value = target
  document.documentElement.lang = target
  localStorage.setItem('locale', target)
}
```

若应用支持从右到左的语言，还要同时设置 `document.documentElement.dir` 并检查布局中是否错误地把 `left`、`right` 写死。浏览器语言可以作为第一次访问时的建议，账户设置和 URL 中的明确选择通常优先级更高。

## 日期、时区和格式化要有产品规则

`new Date('2024-07-12')` 这类字符串在不同环境的时区语义容易让人误解。生日、账期等“日期”不应先转成某一时刻再格式化；订单创建时间这类“时刻”则应明确存储时区或 UTC，再根据用户或业务时区显示。

数字、百分比和货币也需要业务规则：价格的币种由商品还是用户地区决定，金额的四舍五入由前端还是服务端负责，哪些单位需要本地化。`Intl` 和 i18n 库负责格式化，不能替系统决定这些含义。

## 发布前检查

- 缺失翻译键在开发和 CI 中可见，不能静默输出键名到生产页面。
- 长文本、德语等较长单词和窄屏布局不会截断主要操作。
- 语言切换后 `<html lang>`、标题、表单提示和路由中的可翻译内容同步更新。
- 货币、日期、时区和复数由目标语言与业务规则共同验收。
- SSR 与客户端首屏使用同一 locale，避免 hydration 警告和语言闪烁。

国际化质量来自明确的语言与数据规则。库能降低实现成本，但不能替团队决定用户看到的时间、金额和措辞是否正确。
