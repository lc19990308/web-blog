## 前言

去年我还在一篇一篇地看财报、刷新闻，手动整理公司档案。今年我做了一个决定：不再自己当"资料员"，而是**养一匹马**——一个叫 Hermes 的金融研究智能体，让它每天读新闻、扫政策、更新档案、写复盘，我只负责最重要的那部分：**用体感验证它的判断**。

这篇文章记录我从 0 到 100 的完整过程。不是一篇炫技文，而是踩坑实录：每个阶段做了什么、为什么这么做、在哪里翻过车、后来怎么修的。如果你也想搭一个属于自己的研究型 Agent，希望这份地图能帮你少踩几个坑。

> 核心定位先说清楚：**Hermes 不是荐股机器人，是一个长期运行的金融研究系统。**
> 它的价值不是预测股价，而是帮我减少错误、累积可复盘的研究资产。

## 0%：起点——为什么需要"自己的"金融智能体

### 通用 AI 助手的三个致命缺陷

直接用通用 AI 助手做金融研究，我遇到的三个问题：

| 问题 | 表现 |
|:----|:-----|
| 无记忆 | 每次对话都是"失忆重启"，昨天刚建立的判断今天要重新解释 |
| 无纪律 | 随便哪个公众号文章都敢当事实，券商目标价直接当买入理由 |
| 无累积 | 分析完就丢，三个月后回看，找不到"当时为什么这么判断" |

### 我的解法：Agent + 档案 + 纪律

```
用户提问 / cron 定时触发
        │
        ▼
┌─────────────────┐
│  Hermes 分析内核   │ ← LLM 驱动决策
│  (Orchestrator)   │
└───┬───┬───┬───┬──┘
    │   │   │   │
    ▼   ▼   ▼   ▼
  档案  评级  记忆  工具
 (只追加) (S/A/B/C) (持久化) (受限集)
```

三个设计信条：

1. **档案只追加不重写**：同一标的再次分析时先读旧档案，只更新变化，历史判断永远可追溯
2. **先归档后结论**：值得保留的资料必须归档到对应目录，带着 URL、正文和结论
3. **诚实是第一纪律**：区分"事实"与"推断"，不确定就写"未验证"，不编造

## 10%：Hermes Agent 架构设计

### 三层分析流水线

金融研究的骨架是**先行业、后公司**，我把分析拆成三层：

```
第 0 层：板块评级   ── 8 维评分(0-24) → S/A/B/C/D
第 1 层：商业模式   ── 可预测性/ROIC/利润质量/粘性 → 权重 30%
第 2 层：护城河     ── 定价权/品牌/规模/网络效应/转换成本/专利/★趋势 → 权重 40%
第 3 层：管理层     ── 能干/可靠/为股东/段永平测试 → 权重 30%
```

每一层都依赖用户的主观验证——这是系统最大的差异化优势：**AI 负责结构化分析，人负责体感判断**。典型例子：茅台从 S(95) 降到 A(81)，就是因为用户一句"很少喝，白酒味道太重"，护城河趋势从"变宽"修正为"收窄"。

### 评级系统：板块 8 维 + 公司三层加权

| 层级 | 权重 | 检查项 |
|:----|:----:|:-----|
| 第1层 商业模式 | 30% | 可预测性/ROIC/利润质量/客户粘性 |
| 第2层 护城河 | 40% | 定价权/品牌/规模/网络效应/转换成本/专利/趋势 |
| 第3层 管理层 | 30% | 能干/可靠/为股东/段永平测试 |

修正规则：逆向全部通过 +5；1 项红灯 -5；2 项+红灯 -15 或降 1 级；板块 S/A +3，板块 C/D -5。总分映射 S/A/B/C/D，对应"重点买入 / 积极观察 / 配角 / 极便宜才看 / 不碰"。

### 运行宪法（SOUL.md）

最重要的一步：**给 Agent 写宪法**。不是 prompt，而是长期约束：

- 身份边界：是新闻阅读员/政策哨兵/行业研究员，**不是**荐股机器人/短线交易员/情绪放大器
- 工作原则：先一手资料后解读、先行业后公司、先观察后行动、先归档后结论、先复盘后修正
- 信息源纪律：5 级信息源（官方数据 > 公司公告 > 权威媒体 > 行业研究 > 社区情绪）
- 六项禁止：短视频财经号当事实、只看新闻标题判断、单一媒体下结论、券商目标价当买入理由、股吧热帖当依据、"市场都在说"当依据
- 结论前强制扫描 **25 种心理倾向**（Lollapalooza 最危险——多个倾向同向叠加）

### 元认知边界

宪法里最重要的一节是"我知道自己做不到什么"：

```
我能做：结构化分析商业模式/财务/护城河、检查心理偏见、估值比较
我不能做：感受产品体验、判断创始人靠不靠谱、预测年轻人喜好、
        感知市场情绪、发现超额 Alpha
```

> 核心信条：**超额收益来自用户的体感，不是我的分析。我的价值是帮用户减少错误。**

### 数据源：一条自动降级链

行情数据我用"一主一备一兜底"的策略，避免单点故障：

```python
# data_pipeline.py — 自动降级
def get_price(symbol):
    for source in [cnbc_price, sina_price, tushare]:  # 依次尝试
        try:
            return source(symbol)
        except:
            continue
    raise DataUnavailable(f"所有行情源失败: {symbol}")
```

| 级别 | 来源 | 特点 |
|:----:|:-----|:-----|
| 主源 | Tushare + 新浪直连 | 120 req/min，A股/港股/美股通吃 |
| 备用 | Alpha Vantage | 有 Key，但免费版 5 calls/min 太慢 |
| 兜底 | CNBC 无 Key 接口 | QQQ 偶尔不返回时仍可用，60s 缓存 |

### 培养路线：从"养马"到"收官"

我给自己定了一条 7 阶段培养路线，前 6 阶段把 Hermes 养成可控、可持续的研究系统，第 7 阶段收官验收，之后进入**稳态运营**——不再无限加阶段，只做循环维护：

```
主动找资料 → 抽取正文 → 提炼事实 → 生成分析
→ 写入档案 → 更新观察池 → 定期复盘 → 修正模板和规则
```

**验收标准**（第 7 阶段完成标准）：能连续产出日报/政策扫描/周报、能把来源归档到正确目录、能更新档案、能主动指出"这条信息对长期计划没影响"、能在不升级权限的情况下稳定运行。

到这一步，系统完成了从"工具"到"助理"的进化。但这只是 0-30 分，接下来才是最难的：**知识库**。

## 40%：本地知识库——把 570 份文档变成可检索资产

### 需求：研究资料积累到一定量，记忆就开始失效

到第 40 分时，`finance-horse/` 里已经有几百份文档：公司档案、行业研究、政策跟踪、财报分析、复盘记录……靠"每次读全部文件"已经不可能，必须上检索。

我的方案是**双层知识库**：

```
┌─────────────────────────────────────────────┐
│  主账本：/research（Markdown 文件，唯一真源）     │
│  ── 人可读、可审计、可版本管理                   │
└──────────────────┬──────────────────────────┘
                   │ 同步（ragflow_bridge.py）
                   ▼
┌─────────────────────────────────────────────┐
│  检索层：Qdrant 向量库 + 哈希索引                │
│  ── 机器可查、支持混合检索、可重建                │
└─────────────────────────────────────────────┘
```

**设计原则：本地文件是主账本，向量库是可重建的派生层**——任何时刻删掉 Qdrant 都能从 Markdown 重新建起来，绝不把唯一副本放在向量库里。

### 实际规模

| 指标 | 数值 |
|:----|:----:|
| 文档数 | 570 份 |
| 分片数 | 3,907 个 |
| 实体数 | 343 个（中文别名 + 股票代码已标准化） |
| 事实数 | 1,840 条 |
| 关系数 | 2,811 条 |
| 哈希向量索引 | `finance-research-hash-v1`（3,907 点，完整可用） |

### 踩坑：向量模型选型

第一个坑就是**向量模型**。原计划用 BGE-M3（多语言强模型），但实测发现：

1. BGE-M3 索引**一直没完成**（资源占用大、构建时间长）
2. 我用了一个轻量替代：`finance-hash-384-v1` 哈希向量（384 维）

关键认知：**哈希向量分数只是召回信号，不是可信度分数**。召回之后必须经过重排（下一节讲），把向量检索的"可能相关"过滤成"确实相关"。

### 踩坑：VirtioFS 文件锁

第二个坑更隐蔽：macOS 下 Docker 的 VirtioFS 挂载，Qdrant 写数据时文件被锁，导致**读锁冲突**。症状是检索时随机失败、数据写不进去。

修复方案：把 Qdrant 数据迁移到**命名卷**（`finance-qdrant-storage`），不再走 VirtioFS 挂载，彻底避开 iCloud 同步和文件锁问题。

## 50%：RAGFlow——知识库的 UI、解析与检索层

### 为什么需要 RAGFlow

Qdrant 只有向量存储，没有文档解析、分块、重排、研报生成这些能力。RAGFlow 正好补上这一层——它提供知识库 UI、文档解析、检索和生成的工作台。

### 踩坑：磁盘不够，RAGFlow 装不下

这是整个项目**最痛的一个坑**。RAGFlow 完整 Docker 栈包含 Elasticsearch/Infinity/MySQL/Redis/MinIO 等服务，磁盘和内存占用明显高于 Hermes：

```text
macOS / Apple Silicon arm64
Docker server: linux/arm64
当前可用磁盘：约 19GiB
RAGFlow 完整栈需要：至少 60GiB 可用空间  ← 差 3 倍！
```

当时的选择：

| 路径 | 方案 | 结论 |
|:----:|:-----|:-----|
| A | 本机部署，先 `docker system prune` 清理磁盘 | 风险高，`docker volume prune` 可能误删重要数据库卷 |
| B | 部署到 x86 Linux / VPS，Hermes 通过 HTTP API 连接 | ✅ 更推荐，本机只做客户端 |

最终采用**路径 B**：RAGFlow 跑在远程 Linux 机器，Hermes 侧只需要两个环境变量：

```bash
RAGFLOW_BASE_URL=http://<ragflow-host>:9380
RAGFLOW_API_KEY=<your-api-key>
```

## 60%：RAGFlow 检索与重排——从"召回"到"可信"

### 检索模式：混合实体检索

检索不只用向量相似度，我用 `hybrid_entity_vector_keyword` 模式——实体图谱 + 向量 + 关键词三种信号混合。一次典型检索的配置：

```json
{
  "query": "黄金 金价 贵金属 美债收益率 美联储 2026",
  "retrievalMode": "hybrid_entity_vector_keyword",
  "embedding": {
    "mode": "hash",
    "model": "finance-hash-384-v1",
    "collection": "finance-research-hash-v1"
  }
}
```

### 关键设计：召回与重排分离

这是整个知识库最核心的架构决策：

```
原始查询
   │
   ▼
① 混合召回（向量+关键词+实体）→ 25 个候选
   │              ↑ 只求"别漏掉"，召回基准 4/4 通过
   ▼
② DeepSeek 重排 → 重排指令约束
   │              ↑ 只求"过滤噪音"，不编造
   ▼
③ 证据分级 → legacy_unverified / source_unavailable / source_linked
   │
   ▼
④ 生成（仅从引用生成）
```

**重排指令（rerankInstruction）**——防止 LLM 重排时自己编造：

```text
Use the configured DeepSeek model to rerank only these candidates by relevance,
source traceability, date, and numerical consistency. It must not invent a fact
that is absent from these excerpts. The local hash vector score is recall only,
not a credibility score.
```

**生成指令（generationInstruction）**——证据分级约束：

```text
Generate only from cited candidates.
- legacy_unverified        : dated context only（仅历史背景）
- source_snapshot_linked   : preserved source association,
                             does not by itself establish a current fact
- source_unavailable       : cannot support a current claim
If current evidence is insufficient, invoke the source recovery process.
```

### 证据分级体系

每条检索结果都要带上证据等级，这是防止"AI 幻觉当事实"的防火墙：

| 等级 | 含义 | 使用边界 |
|:----|:-----|:--------|
| `legacy_unverified` | 历史背景，未验证 | 仅作背景，不支撑当前事实 |
| `source_unavailable` | 来源已记录但不可用 | 必须写明失败原因 |
| `source_snapshot_linked` | 有快照关联 | 默认 `context_only`，不能单独升级为当前事实 |
| `source_linked` | 有真实一手来源 | ✅ 可支撑当前事实 |

### 检索验收：改动前必须过基准

规则很简单但很硬：**改动检索、实体、向量同步或重排规则前，必须先重新运行检索评估，未通过不得宣称优化已验证。** 当前检索基准 4/4 通过。

## 70%：IMA 远程知识库——把腾讯的知识库变成自己的外脑

### 为什么接 IMA

本地知识库解决"自己的资料检索"，但金融研究还需要**线上的、持续更新的知识**。腾讯 IMA 提供了 16 个金融相关订阅知识库（港股证券知识库、资产评估数据库、产业政策知识库等），等于直接拿到一批别人整理好的金融知识资产。

### 接入方式：官方 OpenAPI 技能包

IMA 官方提供了 OpenAPI 技能包（v1.1.8），统一管理「笔记」和「知识库」两类能力：

- **notes**（笔记）：搜索、浏览、获取、新建、追加笔记
- **knowledge-base**（知识库）：上传文件、添加网页、搜索/浏览知识库、查看原文

### 踩坑：技能包 URL 藏在 JS bundle 里

官方页面是 SPA，下载链接不在页面上。我用了一个很"笨"但有效的方法：**从官方页面的 JS bundle（index-4oPISTJy.js）中提取技能包下载 URL**：

```text
官方页面：https://ima.qq.com/agent-interface
技能包 URL：https://app-dl.ima.qq.com/skills/ima-skills-1.1.8.zip
（从官方页面 JS bundle 中发现，非第三方转载）
```

### 安装前校验：不盲信下载包

受控安装前，我做了四步校验：

| 检查项 | 结果 |
|:----|:----|
| 完整性 | 官方包 SHA-256 记录 + 逐文件校验通过 |
| 静态安全 | node --check 通过；无危险调用（child_process/exec/eval） |
| 网络出口 | 仅 `https://ima.qq.com`（另有一处文档链接非调用） |
| 真实接口 | list_notebook / search_knowledge_base / get_addable_list 全部实测通过 |

### 凭证配置

按官方 SKILL.md 推荐方式，凭证写入本地文件（0600 权限，值不回显）：

```bash
~/.config/ima/client_id   # 0600
~/.config/ima/api_key     # 0600
```

凭证仅作为 HTTP 头发送到 `ima.qq.com`；文件上传使用 IMA API 返回的**短期 COS 临时凭证**，Client ID / API Key 不会发给 COS。

### 长期约定：金融问题优先检索 IMA

接入后我定了一条长期约定：

```
1. 金融相关问题默认先查 IMA 线上知识库（16 个金融订阅库）作为补充参考
2. 查不到或需要实时数据时，再走其他渠道并说明
3. 来源分级：港股证券知识库 = 腾讯自选股一手来源，可信度较高；
   其余 = 第三方二手来源，需交叉验证后才可作为事实
4. IMA 检索结果不替代实时数据通道
```

### IMA 的边界

- 笔记内容属用户隐私：群聊场景只展示标题和摘要，**禁止展示笔记正文**
- 网络出口白名单：`ima.qq.com`（API）+ `*.myqcloud.com`（COS 上传）
- 不支持视频、B站/YouTube 链接、`file://` URL 上传
- notes 写入前必须校验 UTF-8（官方强制规则，防止乱码）

## 80%：质量门禁——让"输出"变得可审计

### 评分器：85 分才够格归档

研究输出不是写出来就完事，要过**确定性门禁** `score-research-report.mjs`：

```
评分维度：
- 来源可追溯性 (35 分)
- 新鲜度       (15 分)
- 分析严谨度   (20 分)
- 数值完整性   (15 分)
- 决策纪律     (5 分)
- 复盘演进     (10 分)
门槛：≥ 85/100 且无校验错误 → 才允许进入正式归档
```

评分是审计辅助，不是"投资结果正确"的证明——这句话写进了规范里。

### 受控归档双通道

早期版本里 Agent 有权限直接写资料库，出了几次"AI 乱写档案"的问题后，我改成**读写分离的侧车架构**：

```
┌──────────┐ 提交请求   ┌──────────────────┐
│ 金融马     │ ────────> │ finance-intake     │  外部来源入库
│ (只读模式) │           │ (独立服务)          │  → 重新拉取 HTTPS → 不可变快照
└──────────┘           └──────────────────┘
       │ 归档请求
       ▼
┌──────────┐           ┌──────────────────┐
│ 金融马     │ ────────> │ finance-archive    │  研报归档
│ (只读模式) │           │ (独立侧车)          │  → 内容哈希 + 评分 + 分类 → 幂等回执
└──────────┘           └──────────────────┘
```

**Agent 永远没有资料库写权限**，所有写入都通过独立服务校验后落库。实测 17 份档案全流程通过，零写库失败。

### 答复审计：每条事实都要能回溯

`audit-finance-answer.mjs` 是交付前最后一道闸：每条事实、推断或判断都必须带 `text`、`kind` 与 `citationChunkIds`；当前事实必须引用 `source_linked` 片段。审计为 `blocked` 时，只能交付信息缺口与补源计划，不能硬答。

## 90%：踩坑大合集——那些让我想砸电脑的时刻

### 坑 1：评分器的"诚实性悖论" ⭐ 最反直觉

整改稿里如实写"当前行情未验证"（诚实标注不确定），**评分器判为 unverified_language 警告并扣 5 分**；改写为"待实时获取"才消除。

> 根因：评分器把"未验证"当作模型记忆污染的信号，但"未验证"正是宪法要求的诚实标注。
> 影响：逼着 Agent 用模糊措辞替代明确的不确定标注，削弱诚实性。

修复：评分器 `UNVERIFIED_PATTERNS` 中移除"未验证"，或改为中性不扣分；保留"训练知识/已知知识/网络不可用"等真正污染信号。

### 坑 2：来源编号解析脆弱

核心数据表来源列写"S3（推算说明）"，评分器误判为 `unknown_source_id`（4 个错误）。表格解析是硬编码的，来源列只接受纯 ID。

修复：来源列做宽松解析（提取纯 ID 部分），模板明确"来源列只写 ID，推算说明放备注"。

### 坑 3：敏感词误伤

批量整改 17 份公司档案时，多份整改稿需要人工改写敏感词——评分器对某些表达过度敏感，导致 Agent 被迫绕弯说话。这暴露了规则设计的"过度防御"倾向。

### 坑 4：重复实体与极简档

知识库里有 5 组重复实体（AI/AMD/MU/QCOM/SONY），344 份旧档里 316 份是 4KB 极简档、34 份较完整、4 份占位文件——全部靠人工判断分流，没有自动化。后来才建立"较完整整改 / 极简挑重点 / 占位删除"的分级策略。

### 坑 5：cron 恢复必须逐项审查

系统重构后所有定时任务暂停，恢复时不能"一把梭"。规则：**每个任务单独验证路径、写入范围和失败处理后才恢复**。10 个 cron 任务逐个过审，防止"脚本存在 ≠ 接口健康"。

### 坑 6：磁盘与文件锁（前面提过，再强调一次）

- RAGFlow 需要 60GiB 而机器只有 19GiB → 改 VPS 部署
- VirtioFS 读锁 → Qdrant 迁移到命名卷

### 通用方法论：坑是怎么被系统化解决的

1. **不把脚本存在当成数据可用**：先跑 `finance-source-status.mjs --offline` 检查渠道状态再选源
2. **查询失败不停止**：先运行来源恢复计划生成渠道顺序，所有允许渠道都要有结果记录
3. **来源回补只追加不覆盖**：在 provenance 目录追加恢复计划、快照、关联和失败记录，绝不改写历史 Markdown

### 四个必须修的短板

1. **评分器"诚实性悖论"**（设计缺陷，优先修）——逼着 Agent 不诚实

## 总结

从 0 到 100，我学到的不是"怎么搭一个 AI Agent"，而是几条更本质的东西：

1. **系统设计 = 信任设计**：Agent 可以自由分析，但不能自由写档案、不能自由下结论、不能自由编造来源
2. **召回与重排分离**：向量分数只是召回信号，可信度要靠重排 + 证据分级来建立
3. **本地文件是主账本**：所有知识库/向量库都是可重建的派生层
4. **诚实是最高优先级**：宁可交付"信息缺口"，不可用幻觉填坑
5. **系统要能自评**：没有打分机制的系统，无法知道自己哪里坏了
6. **养马哲学**：一个长期运行的系统，最重要的不是功能多，而是**稳定、可复盘、不越权**

真正的金融智能体不是预测股价，而是帮助用户更高效地分析信息、减少错误、做出决策——然后让用户自己拿主意。

> 超额收益来自你的体感，不是我的分析。我的价值是帮你减少错误。
