## 前言

做新项目时，技术选型往往是第一道难题。选错了，后期重构成本巨大；选对了，团队开发效率倍增。

本文不推荐"最好的"技术（因为没有），而是给出**不同场景下的选型依据和取舍逻辑**，帮你做出适合自己的决策。

---

## 一、框架选型

### 1.1 主流框架对比

| 维度 | React | Vue 3 | Svelte |
|------|-------|-------|--------|
| **学习曲线** | 中高（JSX + Hooks） | **低**（模板语法简洁） | 低 |
| **生态系统** | **最丰富** | 丰富 | 较小 |
| **性能** | 中等（虚拟 DOM） | 中等（虚拟 DOM） | **最优**（无虚拟 DOM） |
| **TS 支持** | 优秀 | 优秀 | 良好 |
| **国内招聘** | 多 | **更多** | 少 |
| **适合项目** | 中大型、复杂交互 | 各种规模 | 小中型、追求性能 |

### 1.2 选型决策树

```
新项目选框架？
│
├─ 团队熟悉 React？
│   ├─ 是 → React + TypeScript
│   └─ 否 → 继续 ↓
│
├─ 团队熟悉 Vue？
│   ├─ 是 → Vue 3 + TypeScript
│   └─ 否 → 继续 ↓
│
├─ 项目复杂度？
│   ├─ 简单页面（表单/展示）→ Vue 3 或 Svelte
│   ├─ 中后台管理系统 → Vue 3 或 React
│   └─ 复杂交互（编辑器/图表）→ React
│
├─ 国内求职考虑？
│   ├─ 是 → Vue 3（岗位更多）
│   └─ 否 → 按喜好选择
│
└─ 极简 + 极致性能？
    └─ 是 → Svelte
```

### 1.3 不要重新造轮子

```javascript
// ❌ 不推荐
// 为了"锻炼团队"自研框架
// 为了"轻量"不用框架，用 jQuery

// ✅ 推荐
// 使用成熟框架 + 官方推荐的生态库
// 把精力放在业务逻辑上，而不是基建
```

## 二、构建工具选型

### 2.1 主流工具对比

| 工具 | 启动速度 | 构建速度 | 配置复杂度 | 生态 |
|------|---------|---------|-----------|------|
| **Vite** | **极快**（ESM） | **快**（Rollup） | **低** | 丰富 |
| Webpack | 慢（开发 server） | 中等 | 高 | **最丰富** |
| Turbopack | 极快（Rust） | 快 | 中 | 早期 |
| esbuild | **极快** | **极快** | 低 | 有限（无 HMR） |

### 2.2 选型建议

```javascript
// ✅ 新项目首选 Vite
// npm create vite@latest

// ❌ 什么时候考虑 Webpack？
// - 项目依赖了大量 Webpack 插件
// - 老项目维护
// - 需要深度自定义构建流程

// ✅ Vite 配置示例
// vite.config.js
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'

export default defineConfig({
  plugins: [vue()],
  server: { port: 3000 },
  build: {
    rollupOptions: {
      output: {
        manualChunks: {
          vendor: ['vue', 'vue-router', 'pinia'],
          utils: ['lodash-es', 'dayjs'],
        },
      },
    },
  },
})
```

## 三、状态管理选型

### 3.1 什么时候需要状态管理？

```
任何组件都可能访问的数据？

├─ 只在组件内部使用 → 组件局部状态（ref/reactive）
├─ 父子组件共享 → Props + $emit
├─ 兄弟/跨层级 → 考虑 Pinia / Zustand
│
└─ 全局数据（用户登录信息、主题、语言）
    └─ → 需要状态管理工具
```

### 3.2 状态管理方案对比

| 方案 | 框架 | 学习成本 | 体积 | 适用场景 |
|------|------|---------|------|---------|
| **Pinia** | **Vue 3** | **低** | 1KB | 所有 Vue 3 项目 |
| Zustand | React | 低 | 1KB | 简单到中等 React 项目 |
| Redux Toolkit | React | 高 | 12KB | 大型复杂 React 项目 |
| Jotai | React | 低 | 3KB | 原子化状态 |
| Vuex 4 | Vue 3 | 中 | 10KB | 遗留项目 |

**一句话建议：**

```javascript
// Vue 3 → Pinia（不用犹豫）
// React 小项目 → Zustand 或 Jotai
// React 大项目 → Redux Toolkit 或 Zustand
// 没有全局状态需求 → 不要用状态管理
```

## 四、样式方案选型

### 4.1 方案对比

| 方案 | 原理 | 隔离性 | 学习成本 | 适用场景 |
|------|------|--------|---------|---------|
| **Scoped CSS** | data 属性选择器 | 良好 | **零成本** | Vue 项目 |
| **CSS Modules** | 生成唯一类名 | 良好 | 低 | React 项目 |
| **Tailwind CSS** | 原子化工具类 | 良好 | 中 | 快速开发 |
| **Styled Components** | CSS-in-JS | 优秀 | 中 | React 项目 |
| **Sass/Less** | CSS 预处理器 | 无 | 低 | 传统项目 |
| **BEM** | 命名约定 | 手动 | 低 | 任何项目 |

### 4.2 选型建议

```
├─ Vue 3 项目 → Scoped CSS + 少量全局变量
├─ React 项目 → CSS Modules 或 Tailwind CSS
├─ 快速原型 → Tailwind CSS
├─ 组件库开发 → BEM 或 CSS Modules
└─ 追求极致隔离 → Scoped CSS（Vue）或 Styled Components（React）
```

## 六、API 请求方案

| 方案 | 特点 | 适用场景 |
|------|------|---------|
| **fetch** | 原生支持、轻量 | 小项目、简单请求 |
| **axios** | 拦截器、取消请求、上传进度 | **大多数项目** |
| **swr / TanStack Query** | 缓存、自动重试、状态管理 | 数据密集型应用 |
| **trpc** | 端到端类型安全 | 全栈 TypeScript |

**推荐组合：**

```javascript
// 中小项目：axios + 手动管理请求状态
// 数据密集型：TanStack Query（React）/ Pinia 缓存（Vue）
```

## 八、完整技术栈推荐

### 场景 1：个人博客 / 文档站

```
框架：Vue 3 或 Hexo（本站）
构建：Vite
部署：GitHub Pages / Vercel
搜索：Algolia / 本地搜索
评论：Giscus / Valine
```

### 场景 2：中后台管理系统

```
框架：Vue 3 + TypeScript
构建：Vite
路由：Vue Router
状态管理：Pinia
样式：Scoped CSS + 组件库（Element Plus / Ant Design）
HTTP：axios
部署：Docker + CI/CD
```

### 场景 3：移动端 H5

```
框架：Vue 3 或 React
构建：Vite
UI：Vant（Vue）/ Ant Design Mobile（React）
适配：postcss-px-to-viewport
性能：图片懒加载 + 路由懒加载
```

### 场景 4：全栈应用

```
前端：React 或 Vue 3
后端：Node.js（Express / Nest.js）或 Go
构建：Vite
数据库：PostgreSQL / MySQL
部署：Vercel + Supabase 或 自建
```

## 总结：选型核心原则

```
1. 团队熟悉度 > 技术先进性
   → 再好的技术，团队不会用也是白搭

2. 渐进式采用
   → 不需要一开始就决定全部技术栈
   → 可以先选好框架，其他按需引入

3. 避免过度设计
   → 小项目不要上微服务、不要上 monorepo
   → 等真正需要时再引入

4. 关注生态和社区
   → 活跃的社区 = 更好的文档 + 更多找到解决方案

5. 没有银弹
   → 每个选择都有 trade-off
   → 理解取舍比找到"最佳方案"更重要
```
