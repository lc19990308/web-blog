模型训好了（78.2%），部署好了（FastAPI + Ollama），接下来是怎么用。决策模型不是聊天机器人，正确的用法是嵌进业务流程，当一个带概率的 if 语句。

## 多维标签：一次调用多路决策

单个意图标签不够。真实业务需要的是多维画像：用户想要什么，有多急，要不要人工，有没有风险。Jev 的核心能力就是一次调用输出多路决策信号。

我们的标签体系分主副两类：

| 类型 | 标签 | 取值 | 用途 |
|------|------|------|------|
| **主标签** | 意图 | 8 选 1（choice） | 用户想要什么 |
| 副标签 | 紧急度 | 0~1 | 处理优先级 |
| 副标签 | 需人工 | 0~1 | 要不要转人工 |
| 副标签 | 情绪 | 平静/困惑/不满/愤怒 | 服务策略 |
| 副标签 | 升级风险 | 0~1 | 投诉可能性 |
| 副标签 | 业务线 | 售后/支付/物流/技术/账户 | 归哪个组 |
| 副标签 | 涉及金额 | 是/否 | 走财务流程吗 |
| 副标签 | 沟通风格 | 礼貌/急躁/啰嗦/强硬 | 话术策略 |
| 副标签 | 期望响应 | 不急/尽快/立即 | 优先级 |

一条对话可以同时命中多个副标签。实测一条投诉样本的输出：

```json
{
  "主标签": {"意图": "complaint", "置信度": 0.95},
  "副标签": {
    "紧急度": 0.1,
    "需人工": 0.91,
    "情绪": "愤怒",
    "升级风险": 1.0,
    "业务线": "售后",
    "涉及金额": "否",
    "沟通风格": "强硬",
    "期望响应": "立即"
  }
}
```

愤怒 + 强硬 + 高风险 + 需人工同时为真。这些信号给代码做路由，比只看一个意图有用得多。如果只看 `intent=complaint`，你不知道该不该加急、该不该转人工、有没有法律风险。

## 混合架构：各干各的擅长事

副标签的实现用的是混合架构。主标签用 LoRA 神经网络，副标签用文本信号规则。这不是偷懒，是实测后的选择。

试过让 0.6B 模型直接输出多字段：`intent=refund, is_urgent=0.35, need_human=0.22, emotion=0.75`。三种输出格式都试了（key=value、编号列表、单行 CSV），意图准确率从 78% 崩到 18-26%。模型会抄示例、会循环、会输出格式错乱。

小模型做分类很好，做多字段回归不行。所以主标签走 LoRA，副标签走规则：

```python
def predict_secondary(dialog, intent, conf):
    user_text = " ".join(d["content"] for d in dialog if d["role"] == "user")
    
    # 紧急度：关键词信号
    urgent = 0.10 + 0.18 * hits(["尽快","快点","立刻","急","催"]) 
             + 0.20 * hits(["马上","赶紧","立即"])
    
    # 需人工：意图基线 + 关键词
    h_base = {"complaint": 0.55, "tech_support": 0.35, ...}[intent]
    human = h_base + 0.16 * hits(["人工","客服","领导","投诉"])
    
    # 情绪：多信号融合
    angry_score = hits(ANGRY_WORDS) + hits(RISK_WORDS) * 0.5
    emotion = "愤怒" if angry_score >= 2 else "不满" if angry_score >= 1 else "平静"
    
    # 升级风险：投诉/曝光/法律信号
    risk = 0.05 + 0.22 * hits(["投诉","曝光","315","律师","赔偿"])
    
    ...
```

规则的好处是可解释、可调、零延迟。坏处是覆盖面有限。如果业务复杂到规则写不下了，可以换一个小分类器（BERT 级别，151M 参数），比让 0.6B 硬啃多字段靠谱。

## 三档路由：概率驱动的分流

这是决策模型最核心的应用模式。模型输出意图和置信度，代码根据置信度走不同路径：

```python
def route(intent, confidence, secondary):
    score = (secondary["需人工"] * 0.4 
           + secondary["升级风险"] * 0.4 
           + secondary["紧急度"] * 0.2)
    
    if secondary["情绪"] == "愤怒":
        score = min(1.0, score + 0.2)
    
    if confidence >= 0.85 and score < 0.4:
        return "auto", "高置信 + 低风险：自动执行"
    if confidence >= 0.60 and score < 0.7:
        return "llm", "中置信/中风险：LLM 复核"
    return "human", "低置信/高风险/情绪升级：转人工"
```

三档不是只看置信度，还融合了副标签。同样是 confidence=0.8，情绪平静的走 auto，情绪愤怒的走 human。

阈值用的是温度校准后的概率。没校准之前，模型说 85% 实际只有 66% 对，阈值是不可信的。校准后 85% 就真是 85% 把握。

实测路由效果：

| 场景 | 意图 | 情绪 | 风险 | 路由 |
|------|------|------|------|------|
| 含蓄退款 | refund_request | 平静 | 低 | **auto** |
| 愤怒投诉 | complaint | 愤怒 | 1.0 | **human** |
| 技术故障 | tech_support | 困惑 | 低 | **auto** |
| 账单争议 | billing_dispute | 不满 | 中 | **llm** |
| 表扬 | praise | 平静 | 低 | **auto** |

## 和 LLM 协同：分工不是替代

决策模型和 LLM 是协作关系。Jev 只判断，不生成；LLM 负责写回复、做解释。

```
用户消息
   ↓
Jev 决策层（1-2 秒）
   ├─ 意图 + 8 维副标签 + 概率
   ↓
三档路由
   ├─ auto  → 查库/发模板（不调 LLM）
   ├─ llm   → LLM 生成回复（带意图上下文）
   └─ human → 转人工
```

关键点：**LLM 不用每个请求都调。** 简单查询走模板，复杂的才调 LLM。我们实测约 60% 的请求走 auto，25% 走 llm，15% 走 human。省了 60% 的 LLM 调用成本。

auto 场景的回复是模板，比如 `refund_request` + 低风险 → 直接返回退款流程指引。llm 场景会把意图和副标签作为上下文传给 LLM，生成更精准的回复。

## API 用法

FastAPI 服务提供标准 HTTP 接口：

```python
import requests

resp = requests.post("http://127.0.0.1:8765/demo/decide", json={
    "dialog": [
        {"role": "user", "content": "我要退款"},
        {"role": "agent", "content": "订单号？"},
        {"role": "user", "content": "20260928-123，不想要了"}
    ]
})

data = resp.json()
print(data["主标签"]["意图"])       # refund_request
print(data["主标签"]["置信度"])     # 0.99
print(data["副标签"]["情绪"])       # 平静
print(data["路由"])                 # auto
```

批量接口一次处理多条：

```python
resp = requests.post("http://127.0.0.1:8765/demo/decide-batch", json={
    "items": [{"dialog": [...]}, {"dialog": [...]}]
})
```

监控端点看性能：

```python
resp = requests.get("http://127.0.0.1:8765/stats")
# {"requests": 150, "avg_latency_ms": 1200, "cache_hit_rate": 0.62}
```

Ollama 的用法更简单：

```bash
ollama run jev-intent
# 或 API
curl http://127.0.0.1:11434/api/generate \
  -d '{"model":"jev-intent","prompt":"...","stream":false}'
```

## 业务接入的实用建议

**接缓存。** 相同对话直接返回缓存。我们用 LRU 缓存 1024 条，命中率 62%，命中时 0ms。客服场景重复问题很多，缓存收益大。

**阈值先保守。** auto 的阈值定 0.85，宁可多走 LLM 也不要误自动。线上跑一周，收集 badcase 后再调低。

**记录 badcase。** 模型判错的样本收集起来，下一轮训练加进去。数据飞轮转起来，模型会越用越准。

**副标签叠加规则。** 比如「情绪=愤怒 且 风险>0.7」强制转人工，不用看置信度。业务规则比模型阈值更可控。

**批量处理用 batch 接口。** 比循环调单条快，模型只加载一次。

## 换任务：同一套流程

这套流程不只适用于客服意图。我们用同一个 Qwen3-0.6B 基座训了一个斗地主 AI：

| | 客服意图 | 斗地主 |
|--|---------|--------|
| 输入 | 多轮对话 | 手牌 + 桌面 + 对手剩牌 |
| 主标签 | 意图分类 | 出什么牌 |
| 副标签 | 情绪/风险/紧急 | 胜率/炸弹/策略 |
| 核心策略 | 置信度路由 | **必输局不炸** |
| 数据量 | 1082 条 | 2497 条 |
| 训练时间 | 73 秒 | 8 分钟 |

必输局不炸的实现就是在训练数据里标注：当 `win_probability < 0.2` 时，`use_bomb = "否"`。模型学会了「快输了就省着点用炸弹」。

数据生成用规则引擎标注最优出牌，LoRA 训练 8 分钟，官方 converter 转 GGUF 导入 Ollama。基座没变，只换 LoRA adapter（9MB）。

这就是 LoRA 的威力：**同一个基座，不同的 adapter，不同的任务。** 9MB 就是一个新任务。决策的范式（状态 → 类型化判断 → 概率路由）是通用的，换数据就能换场景。
