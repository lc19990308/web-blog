## 先区分“报错”和“恢复”

用户不该因为一个卡片出错就看到整页空白，但也不能把所有异常都塞给 `window.onerror` 后假装页面已经恢复。错误处理至少有三类责任：

- **预期失败**：接口超时、空数据和权限不足，由页面状态明确展示并提供下一步。
- **组件渲染异常**：把失败限制在一个可替换的区域，保住导航和其他内容。
- **未预期异常**：记录足够的上下文，交给监控系统和修复流程，而不是临时改 DOM 掩盖它。

这三类路径会同时存在。把“上报到监控”和“展示降级 UI”拆开，代码才不会在出错时做出错误的恢复动作。

## 组件边界只保护它的子树

Vue 的 `onErrorCaptured` 或 `errorCaptured` 可以捕获后代组件在渲染、事件和生命周期中抛出的错误。边界组件本身的 `setup` 出错，或边界以外的代码出错，仍需要更上层的处理。因此边界要放在独立、可失败的功能外侧，例如报表、富文本预览或第三方图表。

```vue
<!-- WidgetBoundary.vue -->
<script setup lang="ts">
import { onErrorCaptured, ref } from 'vue'
import * as Sentry from '@sentry/vue'

const failure = ref<Error | null>(null)
const resetKey = ref(0)

onErrorCaptured((error, instance, info) => {
  failure.value = error instanceof Error ? error : new Error(String(error))

  Sentry.captureException(error, {
    tags: { boundary: 'widget' },
    extra: { info, component: instance?.$options.name },
  })

  return false
})

function retry() {
  failure.value = null
  resetKey.value += 1
}
</script>

<template>
  <section v-if="failure" role="alert">
    <h2>此区域暂时无法显示</h2>
    <p>可以重试，其他内容不受影响。</p>
    <button type="button" @click="retry">重试</button>
  </section>

  <div v-else :key="resetKey">
    <slot />
  </div>
</template>
```

`return false` 会阻止错误继续向上传播，适合已经在边界中上报并显示降级 UI 的场景。边界应给用户一个可理解的动作，例如重试、返回列表或联系支持；不要把原始错误信息直接显示在生产页面。

## 全局处理器负责记录，不负责重建界面

应用级处理器是最后的观测点。它适合记录组件名、错误阶段和 release，不知道当前哪个区域能安全重渲染，因此不应该在这里强行显示一个全局 fallback。

```ts
// main.ts
const app = createApp(App)

app.config.errorHandler = (error, instance, info) => {
  reportError(error, {
    source: 'vue',
    component: instance?.$options.name,
    info,
  })
}

window.addEventListener('unhandledrejection', (event) => {
  reportError(event.reason, { source: 'unhandledrejection' })
})

window.addEventListener('error', (event) => {
  if (event.error) {
    reportError(event.error, { source: 'window.error' })
  }
}, true)
```

开发环境不要无条件调用 `preventDefault()` 或让 `window.onerror` 返回 `true`。那会吞掉浏览器控制台原本可见的错误，反而让排查变难。生产环境也应按错误类型去重和采样，避免一次循环异常制造上千条同样的事件。

## 请求失败要展示真实状态

接口失败时，随手回填一份“游客资料”或旧的业务数据，可能让用户误以为操作成功。更稳妥的做法是显式维护 `loading`、`error` 和 `data`，只在缓存确实仍可使用时标记它的更新时间。

```ts
import { onBeforeUnmount, ref } from 'vue'

const data = ref<Report | null>(null)
const error = ref<string | null>(null)
const loading = ref(false)
let controller: AbortController | null = null

async function loadReport() {
  controller?.abort()
  controller = new AbortController()
  loading.value = true
  error.value = null

  try {
    const response = await fetch('/api/report', { signal: controller.signal })
    if (!response.ok) throw new Error(`Request failed: ${response.status}`)
    data.value = await response.json()
  } catch (caught) {
    if ((caught as Error).name !== 'AbortError') {
      error.value = '报表暂时无法读取，请稍后重试。'
      reportError(caught, { source: 'report.load' })
    }
  } finally {
    loading.value = false
  }
}

onBeforeUnmount(() => controller?.abort())
```

只对幂等请求或经过产品确认的操作自动重试。创建订单、提交表单这类写操作若因网络中断而重试，可能造成重复提交；应使用幂等键并把最终状态交给服务端确认。

## 资源失败在资源附近处理

图片、广告位和第三方脚本的失败不应依赖全局事件“抢救”。图片组件直接处理 `error`，能替换占位内容，也能保留 `alt` 文本：

```vue
<script setup lang="ts">
import { ref } from 'vue'

defineProps<{ src: string; alt: string }>()
const failed = ref(false)
</script>

<template>
  <img v-if="!failed" :src="src" :alt="alt" @error="failed = true">
  <div v-else role="img" :aria-label="alt">图片暂时无法显示</div>
</template>
```

第三方 SDK 则应提供一个不依赖该 SDK 的核心路径。例如地图加载失败时显示地址和外链，而不是让结算流程一起失效。

## 上线检查

- 让一个子组件主动抛错，确认只有该区域进入 fallback，导航和其他模块仍可操作。
- 让边界组件自己抛错，确认更高一级的处理器能够记录异常。
- 模拟 4xx、5xx、断网和路由离开，检查请求状态、取消和重试按钮。
- 打开监控事件，确认包含 release、环境和非敏感的组件上下文。
- 用键盘访问 fallback，确认焦点顺序和按钮语义没有被错误状态破坏。

优雅降级的目标不是隐藏故障，而是让用户知道当前哪些能力可用，并让团队获得足够的信息修复问题。
