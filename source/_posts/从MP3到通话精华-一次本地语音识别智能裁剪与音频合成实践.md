手里有一段客服电话录音，我需要从里面挑出几轮关键问答，整理成一份方便汇报的精华音频。

要求听起来很简单：保留问题、保留对应回答，去掉无关的铺垫和过长空白。但真做起来，光知道“我要哪几句话”还不够。得找到它们在音频里的位置，判断前后哪些话必须保留，再处理句子之间的衔接。删得太少，录音还是拖沓；删得太狠，可能把半个字切掉，或者把对话剪成另一种意思。

这次我用的办法是：**先让本地语音模型把 MP3 转成带时间信息的文字，再让 AI 助手读取文字、辅助选择片段，最后交给 FFmpeg 执行裁剪和合成。**

这篇记录这条流程怎么走通，以及哪些地方不能完全交给自动化。

## 一、先说清楚：用的到底是什么模型

本次语音识别用的是 **Whisper 多语种 small 模型**，模型文件是 `ggml-small.bin`，约 465 MB。运行它的工具是 **whisper.cpp**，本机调用的命令是 `whisper-cli`。

这几个名字容易混在一起，分别说明一下：

| 名称 | 在这次工作里的作用 |
|:--|:--|
| Whisper | 将语音转换为文字的自动语音识别模型 |
| 多语种 small | 实际使用的模型规格，支持中文；没有使用英语专用的 `small.en` |
| whisper.cpp | 在本机运行 Whisper 模型的 C/C++ 实现 |
| AI 助手 | 阅读转写内容，结合我的要求辅助定位问答、组织剪辑方案、调用工具 |
| FFmpeg / ffprobe | 执行音频转换、裁剪、停顿处理、拼接和文件检查 |

**在本地运行的是语音识别模型。** 这次没有另外部署一个本地大语言模型来判断剪辑内容。语音转写在本机完成，没有将音频上传给云端转写服务；这也不等于 AI 助手的所有文本处理都离线。

选择 small 是这次实际采用的方案。我没有对多个模型做完整速度和准确率对比，也没有记录可用来做性能结论的基准数据。

## 二、把任务拆成几步，反而更容易做好

整条流程可以写成：

```text
原始 MP3
   ↓
whisper.cpp + 多语种 small：本地转写
   ↓
TXT / SRT / JSON：获得文字和时间信息
   ↓
AI 助手读取文字，结合需求提出候选区间
   ↓
结合原录音与用户反馈调整切点
   ↓
FFmpeg：分段裁剪 → 停顿处理 → 按顺序合成
   ↓
成片检查，并保留原音与分段文件
```

Whisper 提供“这里大概说了什么、发生在什么时候”的索引。FFmpeg 按明确的时间和滤镜参数处理音频。中间“哪些内容值得保留”的判断，需要结合任务目标和对话上下文。

我说的“智能裁剪”，指的就是这个有反馈的协作过程：用语义帮助找到片段，再用音频工具执行编辑。

下面的命令是按本次工作整理的复现示例，统一使用通用文件名。它们不是历史终端命令的逐条回放，时间区间和滤镜参数也需要按自己的录音调整。

## 三、先把 MP3 变成可阅读、可定位的文字

### 3.1 准备工具和模型

本次环境是 macOS，使用 Homebrew 安装工具：

```bash
brew install whisper-cpp ffmpeg
```

安装程序和准备模型是两件事。还需要从 whisper.cpp 官方说明指向的模型来源取得多语种 `small` 的 `ggml-small.bin`，放到自己选定的位置。

本文后续示例假设模型保存在 `models/ggml-small.bin`，原音叫 `input.mp3`。模型下载完成后，本地推理不需要再调用远端语音识别接口。

可以先查看当前安装版本的参数：

```bash
whisper-cli --help
```

### 3.2 原音保留，工作文件单独放

我把原始 MP3 和处理过程分开保存。用于识别的音频、转写结果、临时切片都属于可重新生成的工作文件。

```bash
mkdir -p work segments output
```

本机这版 `whisper-cli` 支持直接读取 MP3。为了让复现流程更明确，也可以先生成 16 kHz、单声道、16-bit PCM 的识别用 WAV：

```bash
ffmpeg -n -i "input.mp3" \
  -ar 16000 -ac 1 -c:a pcm_s16le \
  "work/input-16k.wav"
```

`-n` 表示遇到同名文件时不覆盖。这个 WAV 用于识别，后面剪辑仍从原始 MP3 提取，不必把交付音频也降成识别用的采样率。

### 3.3 一次输出三种结果

```bash
whisper-cli \
  -m "models/ggml-small.bin" \
  -f "work/input-16k.wav" \
  -l zh \
  -otxt -osrt -oj \
  -of "work/transcript"
```

几个关键参数的作用：

| 参数 | 作用 |
|:--|:--|
| `-m` | 指定模型文件 |
| `-f` | 指定输入音频 |
| `-l zh` | 指定中文识别 |
| `-otxt` | 输出纯文本，便于阅读全文和搜索 |
| `-osrt` | 输出带时间信息的字幕 |
| `-oj` | 输出 JSON，便于后续程序读取 |
| `-of` | 设置输出路径前缀，不带扩展名 |

TXT 用来理解内容，SRT 用来定位，JSON 留给需要结构化处理的环节。这次项目里也保留了这三类转写结果。

## 四、读取转写以后，先选问答，再定切点

这次录音谈的是显卡算力与测试环境。我需要保留的主线是：来电者提出问题、客服回应环境因素、最后说明后续对接方式。

因此，给 AI 助手的要求需要具体到内容和剪辑约束。例如：

> 读取带时间信息的转写，找出问题描述、环境因素回应和后续对接建议。保留双方关键问答，删除无关铺垫。先列出候选时间段及保留理由，不要把客户的判断写成客服确认，也不要把转写时间直接当作最终切点。

关键词有助于缩小范围，但选段时必须看完整的一轮对话。只留下客服的一句“可能是环境问题”，听众未必知道它在回答哪个问题。反过来，删掉一个限定条件，也可能让回答显得比原意更肯定。

经过调整，主要保留了录音一中的三个区间：

| 片段 | 相对原音的候选区间 | 内容 |
|:--|:--|:--|
| 第一段 | 00:16–01:15 | 来电者描述标称与实测问题 |
| 第二段 | 02:27–03:17 | 来电者补充实测，客服回应环境因素 |
| 第三段 | 03:18–04:00 | 理论数据、说明诉求及商务对接建议 |

第三段后来又按要求删除了内部两处内容，所以这张表描述的是最初保留的范围，不能用来直接还原最后的成片。

### 一个实际踩到的坑：文字边界不等于声音边界

自动转写可能识别错词，也可能把多句话放在同一个时间段里。双方抢话时，说话人归属尤其容易混淆。

这次还有一个具体问题：直接对 MP3 设置转写偏移和时长时，曾出现输出文字超出预期区间的情况。后来需要局部定位时，采用的办法是**先用 FFmpeg 物理截出短音频，再单独识别**。

```bash
ffmpeg -n -i "input.mp3" \
  -ss 198 -t 42 \
  -ar 16000 -ac 1 -c:a pcm_s16le \
  "work/boundary.wav"

whisper-cli \
  -m "models/ggml-small.bin" \
  -f "work/boundary.wav" \
  -l zh -otxt -osrt -oj \
  -of "work/boundary"
```

这里有个小细节：短音频里的时间从零开始。假如识别结果显示某句话从 5 秒开始，它在原音中的位置就是 `198 + 5 = 203` 秒。记录切点时必须说明时间相对于哪个文件。

## 五、先导出分段，修改起来更直接

选好区间后，我没有马上把所有内容做成一个文件，而是先分别导出 WAV。

下面两条命令对应前两个区间，统一输出为 48 kHz、单声道 PCM，方便后续处理和拼接：

```bash
ffmpeg -n -i "input.mp3" \
  -ss 16 -t 59 \
  -ar 48000 -ac 1 -c:a pcm_s16le \
  "segments/01.wav"

ffmpeg -n -i "input.mp3" \
  -ss 147 -t 50 \
  -ar 48000 -ac 1 -c:a pcm_s16le \
  "segments/02.wav"
```

`-ss` 指定开始位置，`-t` 指定持续时间。示例把它们放在输入之后，并重新编码为 PCM；没有采用 MP3 直接流复制来追求精确的句子切点。

分段的好处很快体现出来：用户认可前两段后，后续可以只处理第三段，不必每次把整段录音全部重做。

如果要删除某一段内部的话语，可以把保留区间裁出来再连接。下面只是演示：从第三段候选范围中删除原音 222–225.7 秒，保留两侧内容，并不代表这次第三段全部修改记录。

```bash
ffmpeg -n -i "input.mp3" \
  -filter_complex \
  "[0:a]atrim=start=198:end=222,asetpts=PTS-STARTPTS[a]; \
   [0:a]atrim=start=225.7:end=240,asetpts=PTS-STARTPTS[b]; \
   [a][b]concat=n=2:v=0:a=1[out]" \
  -map "[out]" -ar 48000 -ac 1 -c:a pcm_s16le \
  "segments/03-edited.wav"
```

`atrim` 截取保留区间，`asetpts` 将每段时间戳归零，`concat` 再把它们接起来。

命令执行成功，只说明音频按指定区间生成了。接缝有没有残字、半个音节或突然变化，仍需要回到声音本身检查。

## 六、停顿处理：紧凑和自然之间要留一点空间

用户对成片提出过一个很明确的要求：**缩短对话间过长的空白，但保留自然停顿，不要全部删光。**

这比“删除静音”更具体。短暂停顿承担了换人说话、句子结束和思考的作用，全部挤掉会让对话听起来像连续抢话。

### 6.1 先检测静音区间

FFmpeg 的 `silencedetect` 可以帮助查看低于阈值的区间：

```bash
ffmpeg -hide_banner -i "segments/01.wav" \
  -af "silencedetect=noise=-38dB:d=0.7" \
  -f null - 2> "work/silence-01.log"
```

这个示例检测低于 `-38 dB`、持续至少 `0.7` 秒的区间。阈值需要按录音噪声和说话音量调整，不能把它当成所有通话都适用的值。

检测也只提供声音强弱的信息。轻声的字、气声和电话背景噪声，都会影响判断。

### 6.2 这次实际尝试的自动处理

工作记录中使用过这样的滤镜：

```text
silenceremove=start_periods=0:stop_periods=-1:stop_duration=0.35:stop_threshold=-38dB
```

对各分段处理后，还分别添加了 0.3 秒前置静音，再进行拼接。

这里需要纠正一个容易出现的理解：**`stop_duration=0.35` 不能保证每一处静音最终都恰好保留 0.35 秒。** 它参与滤镜对静音的判断，并不是一句“把所有停顿统一设为这个长度”的指令。

这次记录显示，三段合并版约为 146.54 秒，处理后的自然衔接版约为 134.368 秒，缩短约 12.17 秒。这些数值来自当时的工作记录，不能据此推出每个接缝都自然。

### 6.3 如果还要精修，下一步怎么做

对于听感要求更高的版本，我会采用更明确的方式：检测长静音，保留其前后两端，只删除中间一部分，再逐处试听。这能清楚控制每一处停顿实际留下多少。

这是后续精修方案，不是本次已经逐处完成的处理。当前自动检测没有发现超过 0.7 秒的静音，但这也不能证明没有误删轻声内容，或所有衔接都已达到预期。

## 七、切片合成，最后再输出 MP3

各分段确认后，统一音频参数，再按顺序合成。下面以三份处理后的 WAV 为例；如果第三段有修改，就把第三个输入替换为对应版本。

```bash
ffmpeg -n \
  -i "segments/01.wav" \
  -i "segments/02.wav" \
  -i "segments/03-edited.wav" \
  -filter_complex \
  "[0:a]asetpts=PTS-STARTPTS[a0]; \
   [1:a]asetpts=PTS-STARTPTS[a1]; \
   [2:a]asetpts=PTS-STARTPTS[a2]; \
   [a0][a1][a2]concat=n=3:v=0:a=1[out]" \
  -map "[out]" -c:a pcm_s16le \
  "output/merged.wav"

ffmpeg -n -i "output/merged.wav" \
  -c:a libmp3lame -q:a 2 \
  "output/highlights.mp3"
```

中间保留 WAV，最后生成方便分享的 MP3，可以减少反复有损编码。

这次还保留了原音、转写、分段和处理副本。这样的文件组织有助于回答一个实际问题：如果第三段需要再删一句，应该改哪一份，而不是凭哪个文件名带着“最终版”来猜。

## 八、成片检查要分清检查到了哪一层

文件生成后，可以先查看格式和时长：

```bash
ffprobe -v error \
  -show_entries format=duration:stream=codec_name,sample_rate,channels \
  -of json "output/highlights.mp3"
```

再做一次全量解码检查：

```bash
ffmpeg -v error -i "output/highlights.mp3" -f null -
```

不过，验证不能只停留在文件是否可读：

| 检查 | 能确认什么 |
|:--|:--|
| 格式与全量解码检查 | 音频文件能够被读取、解码 |
| 静音检测 | 是否存在满足当前阈值的长静音 |
| 成片重新转写 | 辅助排查成片可能缺少或多出了哪些内容 |
| 人工回听原音和成片 | 确认切点、问答关系、听感和语义是否符合要求 |

这次的工作记录包含解码检查和静音检查，也有用户对前两段的认可；但没有完整人工听审的记录，个别说话人归属和第三段切点仍需要核实。

尤其不能直接拿早期完整转写当作成片逐字稿。删改以后，成片包含的内容已经变了，原文里有的话，成片未必还在。

## 九、这套方法适合什么时候用

对我来说，它适合处理这样的任务：已经有录音，也知道大致要保留什么，但不想反复拖动进度条找位置。

本地 Whisper 把声音变成可搜索的文字和时间索引；AI 助手帮助将“我想留下这些问答”转成候选区间；FFmpeg 把区间落实成独立切片和合成音频。用户反馈再推动局部修改，过程比较容易追溯。

真正需要花心思的地方，是决定一句话的上下文该留到哪里，以及一句话之后应该停多久。

做完这次以后，我会把流程固定为：**先转写、再选段，先检查分段、再合成，最后回到成片核对。** 原始录音始终保留，所有自动识别和剪辑结果都可以重新生成。
