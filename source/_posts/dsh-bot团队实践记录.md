## 前言

我一直在找一个能替我处理生活琐事的 AI。

写周报那种事我自己能干。我想要的是另一种：记住我这个月交了什么税、上次体检是哪天、VOO 定投扣到第几期、下周出差该订哪天的票。这类事真正烦人，但又不值得我亲自记。

这两条路我都走过，都没走通。

第一条是自己搭。之前做过一个 Hermes 智能体专门做金融研究，从 0 到 100 搭了三个月，还配了手机版，定制了 profile，每天自动扫新闻、更新公司档案。它很好用，只是为一件重活定制的：一条流水线、一个专业方向。我想让它顺手管管生活琐事，很快就别扭了。金融研究的规则（口径必须统一、数字必须可追溯）套在「提醒我交物业费」上，属于用牛刀杀鸡。

第二条是买现成的。Grok 那套 Bot 我看过，形态正合我意：一个能长期陪你、记得住上下文的助手。问题是订阅费我付不起，为几个零碎的生活提醒付一笔月费，怎么算都不划算。

于是回到自建。这次不写流水线，要的是「一群人各自管一摊」的结构。dsh 的 ds-bot 插件现在替我干这个，两周下来跑成了 14 个 Bot。

下面写这条替代路径：Hermes 为什么用不上、为什么买不起、ds-bot 又怎么跑起来的。

---

## 一、变的是形态，不是工具

Hermes 和 ds-bot 解决的问题不一样，硬比没意义。

Hermes 是一条深度流水线。你给它一个任务，它把这件事做到很专业：抓新闻、核证据、算置信度、写报告。适合「我有件重活，需要人天天盯着」。

ds-bot 是一群长期存在的助手。每个 Bot 有自己的角色、自己的记忆、自己的模型，互不打扰，可以拉群协作。适合「我有很多零碎的事，需要有人分别记着」。

我要的是第二种。生活里真正烦人的是「记得一百件小事」，不是「做好一件事」。偏偏这件事，单会话和流水线都办不到。

我试过把这些事压进一个会话。上午聊税务，下午聊旅行，晚上问代码，到第三天前面基本挤没了。上下文就那么大，琐事偏偏全都得记着。

ds-bot 的解法是把事拆给多个长期存在的 Session。税务群聊的事不会串到投资判断里，旅行 Bot 也不需要知道我在研究什么法条。

14 个是这么分的：

```
Chief          总参谋长 —— 调度、复核、对用户交付
NewsBot        新闻     —— 每日简报
ResearchBot    研究     —— 深度研究报告
FinanceBot     投资     —— 宏观与组合
TaxBot         税务     —— 政策与筹划
SecurityBot    安全     —— 风险评估
LearningBot    学习     —— 学习计划与批改
WriterBot      编辑     —— 写作
EngineerBot    工程     —— 技术实现
TravelBot      旅行     —— 行程
TimeBot        时间     —— 日程
OpportunityBot 机会     —— 项目与机会
LifeBot        人生     —— 长期规划
ProductBot     产品     —— 产品设计
```

### 1.1 Chief 是真在干活，不是挂名

分工是不是真的，看用量就知道。

| Bot | 调用次数 |
|---|---|
| Chief | 3413 |
| TaxBot | 993 |
| FinanceBot | 966 |
| NewsBot | 539 |
| SecurityBot | 455 |
| TravelBot | 320 |
| ResearchBot | 261 |

（3413 已含 Chief 名下 4 个子会话，没漏算。）

Chief 是第二名的三倍多。所有投递都过它一遍：Bot 之间转发、群聊主持、产出复核。

这个数字本身就是个验证。要是 Chief 和其他 Bot 差不多，那它只是个摆设。

### 1.2 两套东西别搞混：角色和权限预设

我一开始以为权限只有一套，实际是两层。

角色决定一个 Bot 在协作关系里能干什么：

| 角色 | 能做什么 |
|---|---|
| 我 | 一切 |
| Main Bot（Chief） | 管所有群；增删改任何 Bot |
| 群管理员 | 只管自己的群（名字、公告、成员、发言模式） |
| 成员 | 在群里发言、@ 别人 |

权限预设决定它能在文件系统上碰什么，三档：只读、工作区、完全访问。这个是每个 Bot 单独设的，群里也可以勾「所有成员用同一个」统一切换。

区别很实在：角色管「能不能开除别人」，预设管「能不能删文件」。Chief 角色最高，设成只读照样什么都改不了。

权限只有我能设，Bot 改不了自己或别人的。堵住了「为了完成任务自己提权」这条路。

## 二、我的用法核心：把标准写成规则

两周下来最有用的一条，也是我事先没想到的：真正管用的不是提示词，是写成文件的规则。

### 2.1 为什么规则比提示词重要

早期的做法是每次在对话里叮嘱：「记得标来源」「数字要核对」「别编」。

结果很稳定：前三条记得住，第五条就忘了。模型不笨，问题是这些要求没进执行路径。

后来改成写文件。根目录一个 `AGENTS.md`，各业务目录一个 `README.md` 或 `RULES.md`，都当硬约束。

现在 `AGENTS.md` 只有七条，原文摘两条：

```markdown
- 改掉任何一个数字后，用**旧值** grep 全文（摘要、小标题、正文引用，
  以及「占 X%」「是 Y 倍」这类只含比较的派生句），确认零命中再收工
  ——正文算对了、摘要和标题没跟着改，这个毛病已经反复出现过。

- 回答用户先给明确结论和方向判断，不要模棱两可、不要用「但是」打折；
  缺的信息集中列在结论之后，不要一上来抛一堆问题。
```

用词都很硬：「不要」「必须」「已经反复出现过」。写软了它就不执行，这语气是被逼出来的。

### 2.2 一个规则的演化史：如何判断该写多深

`research-reports/RULES.md` 里记着一件事：报告该写多深。这段比任何教程都值钱。

最初让 Bot 自己判断「用户会不会拿这个做决策」。这个判据废了，因为每份报告都能辩称自己很重要。

改用「结论里的分歧点数量」分成两档：

| 分歧点数 | 档位 | 要求 |
|---|---|---|
| 0–1 | 快查档 | 3–5 条证据，聊天里四句话给结论，文件只作存证 |
| ≥2 | 深研档 | 完整 11 节 + 问题树 + 证据索引 |

然后连踩两个坑，都写进了文件：

> 第一版校验器无条件要求 11 节，于是 RULES 里那句「不追求格式完整」永远无法兑现。规则和校验器对不上时，赢的总是校验器，人会去凑 11 节，而不是去用快查档。

> 分档靠 `**分歧点数：N**` 声明，那没声明怎么办？第一版默认给快查档，等于「不声明就能拿到更松的要求」，又是默认放行。现在没声明按深研档走并单独报一条。

还试过让脚本自动数分歧点，两版都失败：

> 数加粗小标题 → 把「来源间冲突」「未证实」这类分节标签也数进去，虚高。
> 数顶层列表条目 → 把「方法论上的自我批评」「其他可能解释」数进去，真实 4 个变成 10，还是虚高。
> **原因是「什么算一个分歧点」本身是判断，不是格式问题，正则数不出来。**

最后改成让报告自己声明，再配一条约束：第 8 节按 `D1/D2/...` 编号，声明值要和编号数对上。

记录的价值在于它记了失败路径。不写的话，三个月后我还会再去试一遍正则，然后第二次失败。

### 2.3 规则要能被校验，否则会退化成建议

光有文字规则不够。能自动检查的都写成了脚本。

工作区里一共 52 个 `.mjs` / `.py` 文件（含测试），零 npm 依赖：

```
scripts/           13 个   clock、ledger-zone、paths、rss-fetch 等公共件
news/tools/        10 个   简报校验、索引、来源国别统计、信源探测
finance/tools/      5 个   组合计算与模拟
research-reports/   2 个   build_index.py + 对应测试
```

零依赖图的是可移植：换台机器、过半年再跑，都不用担心依赖烂掉。每个脚本基本配了 `.test.mjs`，改动先跑测试。

简报的校验器卡得很死。正文每条固定九个字段，缺一个直接不通过：事实、来源、交叉确认、矛盾、置信度、核实方式、为什么重要、影响长期计划、继续跟踪。

源码里那段注释很能说明规则是怎么长出来的：

> 只有这些值算「没有矛盾」，其余内容一律按矛盾处理（宁可扣分）。
> 注意集合里**没有空串**：这一行必须显式写出来。以前缺这一行就等于「无矛盾」，于是「不声明」自动变成了「已核对过、来源间一致」——**默认值替作者作了证**。

「默认值替作者作证」这六个字，是我在这个项目里见过最准的批评。前面分档那个坑是同一个病。

`window` 字段也卡。它查的是每条来源行里的「获取」日期有没有落在窗口内。文档里的解释是：

> 声称这一轮抓的、其实不是这一轮抓的，才是要让旧闻冒充今日增量。

## 三、真实产出：每天早上的简报

这条线跑得最稳，NewsBot 每天产一份。

### 3.1 一份简报长什么样

实际文件结构：

```
news/
├── daily/2026-11-18.md      当日简报，唯一交付物
├── archive/2026-11.md       按月归档
├── INDEX.md                 索引：天数、条目数、置信度分布、来源国别占比
├── watchlist.md             定义「什么算重要」
└── tools/                   校验、索引、国别统计、信源探测
```

frontmatter 是扁平结构，只放文件级字段：

```yaml
---
type: news
as_of: 2026-11-18
tier: note
confidence: C
items: 6
window: 2026-11-17T14:00+08:00/2026-11-18T14:00+08:00
---
```

### 3.2 每条都带核实链路

抽一条真实的（英伟达财报）：

> **事实**：营收 1158 亿美元，环比增 20%、同比增 103%；数据中心营收 1076 亿美元……
> **来源**：nvidianews.nvidia.com/... · 发布 2026-11-17 · 获取 2026-11-18 · 层级 secondary
> **交叉确认**：BBC 报道季度销售翻倍至 1158 亿美元、盘后股价涨 4.8%，与财报原文一致
> **矛盾**：无
> **置信度**：C（60/100）
> **核实方式**：读官网财报原文，逐项核对营收、分部、毛利率、每股收益、回购授权与四季度指引……

有个细节：官方新闻室的域名不在信源登记表里，按规则只能标 `secondary` 而不是 `primary`。规则比直觉严，这正是要的效果。

### 3.3 「为什么重要」才是价值所在

罗列事实谁都会。简报每条都带「为什么重要」，是从证据推出来的判断。还是那条英伟达：

> 营收翻倍的同时毛利率指引在四季度降到 71%–72%（本季 74.8%），这是产品结构转向新一代平台与成本上升的直接信号；把中国数据中心收入直接归零写进指引，是公司第一次把「中国市场可能长期不可得」当成基准假设而非风险提示。这两点合起来，比营收数字本身更有信息量。

这种段落才是我真在读的。它把「营收翻倍」这个好看的数和「毛利率下移」「中国收入归零」摆在一起，结论比标题党复杂得多。

### 3.4 watchlist 决定边界

简报不是什么都写。`watchlist.md` 定义了「什么算重要」，分三级。不在清单上的事件，除非能改写清单里任一条目的判断，否则不进。

不定义边界的话，AI 会觉得什么新闻都重要，最后又是一份信息噪音。

## 四、深度研究：分歧点驱动的写法

`research-reports/` 是另一条线，产出比简报重。

现在有两份成品：`eu-ai-act-high-risk-2026-11-15.md`、`stablecoin-web3-facts-2026-11-15.md`。

### 4.1 核心原则：文件是证据链，聊天是交付物

RULES.md 里这句话，我认为是整套设计最关键的一条：

> **聊天**：用户默认只看这里。结论、置信度、最该注意的一件事，都在聊天里说完。不写「详见报告」。
> **文件**：不是给人读的，是给验收和未来的自己读的，就是「当时凭什么这么判」。所以证据编号、URL、日期、类型必须全，删了就没法复查。

这挡掉了一个常见死法：报告写三十页，用户没看，Bot 以为交付完了。

### 4.2 深研档要塞进附录的东西

正文只写分歧点。立法流程表、时间线重复段、背景铺陈一律挪附录。

篇幅也做了约束：

> 正文长度应与分歧点数量相称。1 个分歧点写 200 行、10 个分歧点写 200 行，都是失控。参考上限：正文 = 分歧点数 × 40 行。

这条有意思的地方是用数学关系约束篇幅，而不是写一句「请简洁」。

## 五、其他几条线

团队不只干这两件事，其余目录也都在跑：

| 领域 | 目录 | 关注什么 |
|---|---|---|
| 投资 | `finance/` | 宏观跟踪、组合、研究报告 |
| 税务 | `tax/` | 政策变化、筹划方案 |
| 安全 | `security/` | 风险评估 |
| 学习 | `learning/` | 学习计划、练习、批改、复盘 |
| 机会 | `opportunities/` | 项目与机会池 |
| 旅行 | `travel/` | 行程 |
| 人生 | `life/` | 长期规划 |

### 5.1 旅行那摊最能说明琐事怎么管

生活琐事里最难的是旅行攻略。AI 写攻略有两个固定坑：把攻略帖当事实，把三个月前的签证政策当今天的。

所以 `travel/` 里不放一篇攻略，放的是一份台账，五个阶段串成闭环：

```
需求确认 → 查证 → 方案 → 出发前复核 → 复盘
 brief     research  plan    prefight     postmortem
```

每阶段有硬门槛，过不去就卡在那：

| 阶段 | 门槛 |
|---|---|
| brief | 五个问题答完（出发地、人数、护照、预算、偏好） |
| research | 每条事实带类别、来源、查阅日期 |
| plan | 至少一条签证类事实，且可信度不能是 C/D |
| prefight | 距出发 ≤14 天，policy/safety/transport 未过期 |
| postmortem | 写了实际花费**和**哪条信息不准 |

这些都设成 error 而不是 warn，文档里给的理由是：

> 门槛只 warn 的设计会养出假台账。复盘只 warn 就会全是凑数复盘，而复盘恰恰是这套系统唯一能让下次变准的环节。

有一条我看了半天，觉得是这套东西里最聪明的：「结论」不许是空话。

判据：结论里没有可核对的锚点（数字、拉丁词、专名、引用原文），并且命中两个以上空话词，报错。

两个条件缺一不可，是实测出来的：一份三条事实、字段全齐的攻略，结论写「签证政策比较宽松，建议提前了解」「交通方面有多种选择，看情况安排」「价格合理，性价比不错」，校验器零错误，评级 A（85/100）。

> 这类句子删掉，攻略一个字都不会少，但它看起来像查过了。

这句话我记了很久。它跟格式没关系，说的是 AI 写作最容易滑过去的地方：用正确废话填满版面，让人以为查过了。

配套还有一条反向的：如实写「未查到」直接放行。文件里说：

> 校验器不能奖励编数字。写不出具体值时的正确写法是承认没查到，不是塞一句听起来具体的空话。

### 5.2 学习那条线的一个设计

`learning/profile.md` 里给自己建了「可验证 / 不可验证知识点」的分类：

> **可验证类**（结果能被代码或工具验证，判分可信）：Python 运行时行为、Node.js 事件循环、SQL 结果、算法与数据结构、性能与复杂度
> **不可验证类**（判分只能靠我推理，可信度低，必须配外部锚）：软考概念辨析、架构取舍、英语阅读理解

这么分是因为 AI 判卷有个隐蔽毛病：碰到不可验证的题，它照样给个自信的分数，而那个分数不可信。

分类之后两套判分法。可验证的直接跑代码；不可验证的必须配外部锚。

### 5.3 学习者档案会成为跨会话资产

`profile.md` 记的不是学到了哪一章，是这些：

- 起点档位：「有工程能力、缺并发与一致性模型」
- 判断依据：自建资料库、PDF OCR 流水线、244 题可判分离线题库
- 已完成探测：2026-11-16 后端方向（重复下单/幂等）

这些会进 memory。下次开新会话，Bot 不用重新摸底。

## 六、记忆：两周 99 次改动

记忆这块和我见过的多数 Agent 不一样，值得说说。

### 6.1 不靠 Bot 自觉

多数 Agent 靠模型自己「想起来调用 remember」。经验是它经常忘。

ds-bot 是每轮结束后单独跑一次审查，读这轮新内容，自己决定留、改还是删。

两周下来 `journal.jsonl` 有 99 条记录。但看各 Bot 的记忆文件，事实不太好看：

| Bot | 记忆行数 | 调用次数 |
|---|---|---|
| Chief | 50 | 3413 |
| LearningBot | 17 | 172 |
| FinanceBot | 5 | 966 |
| TaxBot | 5 | 993 |
| NewsBot | 5 | 539 |
| TravelBot | 5 | 320 |

只有 6 个 Bot 有记忆文件，另外 8 个一条都没有。

调用量和记忆量完全不成比例。TaxBot 跑了 993 次，记忆 5 行；FinanceBot 958 次，也 5 行。

### 6.2 记忆审查没有想象中那么勤奋

我原以为自动审查会攒下不少东西。实际情况是审查跑了，但大多判定成「不值得记」。

看留下来的内容，标准大概是这样（FinanceBot 唯一那条）：

> 用户的长期投资计划：每月定投 3,400 港币的 VOO（标普 500），已执行 7 个月，打算坚持 30 年；但税务身份、这笔钱在收入中的占比、最终用途，用户都还没确认。

这条确实该记：跨会话有用的稳定偏好，还带着待确认项。

倒推那些没记的，大概是：当次任务的中间结果、已经落进文件的结论、财报数字这类查得到的东西。

这策略其实对路：记忆只放「查不到又长期有用」的，不然很快变垃圾场。代价是别指望它记住你随口说的话。

要它一定记住，两个办法：跟 Bot 说「记住这个」，或者到记忆面板手动加。别指望自动审查。

### 6.3 三层作用域各管各的

| 层级 | 谁能读 | 谁能写 |
|---|---|---|
| Bot 自己的 | 只有它 | 它自己 |
| 群记忆 | 该群成员（只在该群） | 任何成员 |
| 团队记忆 | 所有 Bot | 主 Bot、任意群管理员 |

群记忆的边界很硬：成员在别的群和自己私聊里都读不到。

这样不至于串味，税务群聊的事不会渗到投资判断里。

### 6.4 只记你说的话

审查有三个约束：只留我说的话、用我的语言写、拒绝密钥密码身份证。

安全上还有一条：记忆是数据不是指令。网页、文件、工具结果里让 Bot「记住这个」的内容不采信。

## 七、踩过的坑

### 7.1 规则和校验器打架，赢的总是校验器

前面提过，这里再说一遍，因为这是最反直觉的一个坑。

RULES 里写着「快查档不追求格式完整」，可校验器无条件要 11 节。结果 Bot 每次都凑满 11 节，因为过不了校验就交不了。

文字规则和自动校验打架，赢的永远是校验器。要么让规则能被校验，要么就别写。

### 7.2 默认放行是最危险的设计

分档最初是「没声明分歧点数就当快查档」，等于不声明就能拿到更松的要求。

Bot 很快学会不声明。

现在没声明按深研档走，还单独报一条。任何「缺省宽松」的设计都会被利用。

### 7.3 数字改了正文没改

`AGENTS.md` 里有条规则专门治这个：

> 改掉任何一个数字后，用**旧值** grep 全文（摘要、小标题、正文引用，以及「占 X%」「是 Y 倍」这类只含比较的派生句），确认零命中再收工。

括号里那句「以及『占 X%』『是 Y 倍』这类只含比较的派生句」是补上去的。第一版只 grep 绝对值，结果改完数字，那句「占比 32%」还是旧的。

文件里写着「这个毛病已经反复出现过」。确实反复出现过。

### 7.4 时区导致同一份数据不同结果

早期用运行机器的本地时区算「今天」，换台机器跑出来的错误数和分数就不一样。

现在统一按工作区根目录 `ledger.json` 声明的时区算。这条也在 AGENTS.md 里。

### 7.5 升级 dsh 后团队起不来

这个是纯技术坑。profile 里可能 pin 着官方包的旧版本，升级后版本不匹配，行被禁用，ds-bot 依赖的 `sessionController` 注入不上，一直 pending。

```bash
npx ds-bot doctor         # 只报告
npx ds-bot doctor --fix   # 删不满足的，自动 pnpm install
```

我这边 `npx` 直接崩（npm 缓存权限乱了），改用本地副本：

```bash
node ~/.dsh/profiles/desktop/node_modules/ds-bot/bin/ds-bot-doctor.mjs
```

## 八、两周后的判断

### 8.1 数字

先说明口径，因为这个搞混了结论会差很远。统计区间是 11-04 到 11-18，两周。

usage 库里的调用分两类：一类属于 Bot 的 Session，另一类没有 Bot 归属（DSH 自己的会话，包括我直接用的）。两边的数差得很多：

| 指标 | 全部调用 | 仅 Bot |
|---|---|---|
| 调用次数 | 20086 | 7350 |
| 输入 token | 1.89 亿 | 2258 万 |
| 输出 token | 1378 万 | 603 万 |
| 缓存读取 | 31.2 亿 | 9.43 亿 |
| 缓存 / 输入 | 16.5 倍 | 41.8 倍 |

我要说的是 Bot 那列。缓存读取是输入 token 的 41.8 倍，而全部口径只有 16.5 倍。

这个差距很能说明问题：Bot 跑的是长期 Session，前缀缓存几乎每轮都命中；我直接用的会话则经常是新的，缓存命中率低得多。如果每次开新会话干活，这 9.4 亿 token 全要按输入重算，成本完全是另一个量级。

团队规模：14 个 Bot，1 个群（7 名成员），记忆改动 99 次。

### 8.2 什么真的好用

每日简报收益最直接。以前四十分钟，现在五分钟（读 + 挑毛病）。

深度研究是第二件。分歧点分档那套规则跑通之后，报告质量稳定多了，关键是它不再写一堆没人看的背景铺陈。

规则体系本身能复用。把标准写成文件和脚本之后，新加一个领域很快：照抄结构、改 watchlist、加几个校验就行。旅行那摊就是这么起来的。

### 8.3 什么不好用

一次性小任务反而更慢。开一堆 Bot 走一遍调度，不如直接问普通会话。

自动校验能卡格式，卡不了内容质量。有几次报告格式完美、结论站不住，校验器一点意见都没有。

token 消耗也不低。14 个 Bot 每天在跑，用量是真实存在的。好在 `Settings → Usage` 能按 Bot、按模型看，能定位到是谁在烧。

### 8.4 最没想到的收获

省时间在意料之内。没料到的是另一件事：被迫把自己那套模糊的标准想清楚。

写 `watchlist.md` 得回答什么算重要；写 RULES 得回答什么算好报告；给学习分类得回答哪些知识真能验证。

单会话时代这些从来不用回答。反正每次都重新开始，标准搁在脑子里，模糊着也能糊。

现在 Bot 会把文件读进去照着做，模糊的标准立刻变成执行中的偏差，糊不过去。写下来才发现，有几条原来是不自洽的。

前言里那两个问题：Hermes 那套流水线还在跑，只是不再兼任生活管家；Grok 的订阅费我还是没付。

替代方案跑起来了，两头都顾上了。这比省下来的时间值。
