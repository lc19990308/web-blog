## 前言

"组件"是现代前端开发的原子单位。但一个常见的困惑是：

> "这个 Modal 是应该独立成一个组件，还是和页面写在一起？"

好的组件设计没有标准答案，但有**可遵循的原则**。本文将系统讲解组件设计的核心原则。

---

## 一、原子设计理论

Brad Frost 提出的原子设计（Atomic Design）是组件分层的最佳参考：

```
原子（Atoms）     →  按钮、输入框、图标
分子（Molecules） →  搜索栏（输入框 + 按钮）
有机体（Organisms）→ 导航栏（Logo + 搜索栏 + 菜单）
模板（Templates） →  页面骨架
页面（Pages）     →  填充了真实内容的模板
```

```tsx
// 原子 — 基础 UI 元素
function Button({ children, variant }: { children: ReactNode; variant: 'primary' | 'secondary' }) { }

// 分子 — 组合原子
function SearchBar({ onSearch }: { onSearch: (q: string) => void }) {
  return (
    <div>
      <Input placeholder="搜索..." />
      <Button variant="primary">搜索</Button>
    </div>
  )
}

// 有机体 — 组合分子
function Header() {
  return (
    <header>
      <Logo />
      <SearchBar />
      <UserMenu />
    </header>
  )
}
```

## 二、SOLID 原则在前端的应用

### S —— 单一职责

一个组件只做一件事：

```tsx
// ❌ 职责过多：既展示用户信息，又处理编辑逻辑，还处理权限判断
function UserPanel({ userId }) { /* ... */ }

// ✅ 拆分
function UserInfo({ user }: { user: User }) { /* 只展示 */ }
function EditUserForm({ user, onSave }: { user: User; onSave: (data: User) => void }) { /* 只编辑 */ }
function withPermission(Component) { /* 只处理权限 */ }
```

### O —— 开闭原则

对扩展开放，对修改关闭：

```tsx
// ❌ 通过内部判断扩展
function Icon({ name }) {
  switch (name) {
    case 'home': return <HomeIcon />
    case 'user': return <UserIcon />
    // 每加一个图标都要改这里
  }
}

// ✅ 通过组合扩展
function Icon({ children }) { return <span className="icon">{children}</span> }
// 使用：<Icon><HomeIcon /></Icon>
```

### L —— 里氏替换

子组件应该能替换父组件：

```tsx
// 如果 AcceptTermsCheckbox 可以作为 Checkbox 的替换
interface CheckboxProps {
  checked: boolean
  onChange: (v: boolean) => void
}

function AcceptTermsCheckbox(props: CheckboxProps) {
  return (
    <label>
      <Checkbox {...props} />
      我已阅读并同意 <Link to="/terms">服务条款</Link>
    </label>
  )
}
```

### I —— 接口隔离

不要在 props 中传递不需要的数据：

```tsx
// ❌ 传递整个对象，组件只用了两个字段
<UserCard user={user} /> // user 可能包含 password、token 等敏感字段

// ✅ 只传递需要的 props
<UserCard name={user.name} avatar={user.avatar} />
```

### D —— 依赖倒置

高层组件不依赖低层组件的具体实现：

```tsx
// ❌ 直接依赖 API
function UserProfile() {
  const [user, setUser] = useState()
  useEffect(() => { fetch('/api/user').then(setUser) }, [])
  return <div>{user?.name}</div>
}

// ✅ 通过 props 注入（数据源可替换）
function UserProfile({ user }: { user: User }) {
  return <div>{user.name}</div>
}
// 测试时可以传入 mock 数据，而不需要启动服务器
```

## 三、组件组合模式

### 3.1 复合组件（Compound Component）

```tsx
function Select({ children }: { children: ReactNode }) {
  const [value, setValue] = useState()
  return (
    <SelectContext.Provider value={{ value, setValue }}>
      {children}
    </SelectContext.Provider>
  )
}

Select.Option = Option

// 使用
<Select>
  <Select.Option value="1">选项一</Select.Option>
  <Select.Option value="2">选项二</Select.Option>
</Select>
```

### 3.2 Render Props

```tsx
function DataFetcher({ url, children }: { url: string; children: (data: any) => ReactNode }) {
  const [data, setData] = useState(null)
  useEffect(() => { fetch(url).then(r => r.json()).then(setData) }, [url])
  return data ? children(data) : <Loading />
}

// 使用
<DataFetcher url="/api/posts">
  {posts => <PostList posts={posts} />}
</DataFetcher>
```

### 3.3 高阶组件（HOC）

```tsx
function withAuth<P>(Component: React.ComponentType<P>) {
  return function AuthenticatedComponent(props: P) {
    const { user } = useAuth()
    if (!user) return <Navigate to="/login" />
    return <Component {...props} user={user} />
  }
}

const AdminPanel = withAuth(AdminPanelContent)
```

## 四、Props 设计原则

```tsx
// 好的 Props 命名
interface BadgeProps {
  count: number
  variant: 'success' | 'warning' | 'error'
  size: 'sm' | 'md' | 'lg'
}

// 坏的 Props 设计
interface ButtonProps {
  primary?: boolean   // ❌ 布尔命名不好——到底是 primary 还是 primary style？
  show?: boolean      // ❌ 太模糊——show 什么？
  width?: string      // ❌ 不应该让外部控制内部布局
}
```

**5 条 Props 黄金法则：**

1. **避免过多的布尔 props** —— 考虑用 `variant` 枚举代替
2. **不要传递 className 和 style** —— 除非组件确实需要自定义样式
3. **Props 应该是扁平化的** —— 不要传深层嵌套的对象
4. **提供合理的默认值** —— 让组件可以不传任何 props 也能工作
5. **用 TypeScript 严格类型化** —— 约束 props 的合法性

## 五、总结

组件设计是"权衡的艺术"。没有放之四海而皆准的规则，但以下原则可以帮助你做决策：

```
是否可复用？     → 是 → 独立组件
                 → 否 → 和父组件写在一起

是否改变 UI？    → 是 → 可以拆
                 → 否 → 可能是逻辑 hook

props 是否过多？ → 是 → 考虑拆分
                 → 否 → 保持

是否依赖外部数据？→ 是 → 考虑将数据获取与展示分离
```

**最终目标是：** 组件高度内聚、低耦合、可测试、可复用。
