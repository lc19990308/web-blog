前端可访问性（a11y）实战指南

2024-06-204 分钟阅读更新于 2026-11-09

可访问性从语义、键盘和焦点开始，而不是堆叠 ARIA 属性。本文覆盖原生控件、动态提示、颜色、媒体与自动化和人工验收的边界。

先让页面能被理解和操作

可访问性不是在上线前跑一次扫描就结束。它影响键盘用户能否完成操作、屏幕阅读器能否理解页面结构、放大文字后内容会不会丢失，也影响网络慢或资源失败时页面是否仍有意义。

实践时先检查三件事：信息有没有正确语义，所有操作能不能用键盘完成，状态变化是否能被感知。它们往往比给元素添加更多 ARIA 属性更有效。

原生控件优先于模拟控件

原生 button、a、input 和 select 已经包含键盘行为、焦点语义与辅助技术支持。用 div 模拟按钮时，不仅要补 role，还要自己处理 Enter、Space、禁用状态、焦点和名称，出错空间很大。

自定义控件只在原生控件确实无法表达交互时使用，例如组合框、树形控件或拖放排序。此时应遵循对应的 WAI-ARIA 交互模式，而不是只补一个 role。一个有 role="checkbox" 的 div 若没有正确的焦点、Space 键行为和动态的 aria-checked，对使用者反而更难用。

键盘顺序和焦点必须可见

页面的 Tab 顺序应尽量跟随 DOM 顺序。不要使用大于 0 的 tabindex 人为插队，它会让焦点顺序难以预测。tabindex="-1" 只用于需要由脚本聚焦、但不应进入常规 Tab 链的元素，例如打开对话框后的标题。

不要全局移除 outline。如果设计需要自定义焦点样式，也要保证在浅色、深色和高对比背景上清晰可见。打开模态框后，把焦点移入对话框；关闭时还给触发按钮。路由跳转或内容替换后，将焦点移动到新的主标题或主内容区，屏幕阅读器用户才知道页面已经变化。

表单和动态状态要有名称

可见的标签优先于 placeholder。错误信息应说明怎么修复，并和对应字段关联；提交后的异步结果再通过合适的实时区域提示。

role="status" 适合一般完成提示。只有需要立即打断阅读的严重错误才使用 role="alert"。不要在页面初次加载时把大量静态文本放进实时区域，否则屏幕阅读器会重复播报无关信息。

颜色、图像和媒体不能单独承担信息

文字与背景的对比度、非文字界面的边界和状态对比度，都要按目标 WCAG 级别检查。状态不能只靠红绿颜色表达，至少增加文字、图标形状或边框变化。

图片的 alt 要描述图片在当前语境中的作用。装饰图可用空 alt，信息图则应提供用户完成任务所需的摘要或附近的数据表：

视频需要与内容匹配的字幕，纯音频需要文字稿。图标按钮也必须有可访问名称，例如文字、aria-label 或可被辅助技术读取的隐藏文本。

自动检查找不到全部问题

Lighthouse、axe 等工具能发现缺失名称、错误 ARIA 用法和部分颜色问题，适合纳入开发与 CI。但它们无法判断链接文字是否清楚、焦点管理是否合理、弹窗是否打断任务，也无法代替使用屏幕阅读器和键盘走完真实流程。

每次发布前至少进行这几项人工检查：

  • 不使用鼠标，从地址栏进入页面后完成主要流程。
  • 放大页面文字并在窄屏下查看，确认没有横向裁切或重叠。
  • 打开、关闭对话框和路由跳转，确认焦点位置符合预期。
  • 用 VoiceOver、NVDA 或目标平台的读屏工具听一遍标题、表单和状态提示。
  • 对照设计色板检查默认、hover、disabled、错误和选中状态。

可访问性最容易在组件刚设计时做好。等到页面堆满 div 和脚本后再补救，成本会高得多。
