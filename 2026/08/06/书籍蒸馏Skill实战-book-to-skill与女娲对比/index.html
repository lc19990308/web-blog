书籍蒸馏Skill实战：book-to-skill 与女娲人物Skill的对比

2026-08-064 分钟阅读更新于 2026-08-31

把一本书蒸馏成 Agent Skill 的完整实战：book-to-skill 安装、蒸馏《重构》中文版的踩坑过程、与女娲（人物蒸馏）和仓颉的对比、RAGFlow 知识库的三层分工，以及版权与来源核验的教训

前言

你有没有过这样的经历：买一本好书、读一遍、三个月后连第 7 章讲什么都忘了；想靠 AI 回忆，它要么幻觉要么说没读过；想翻 PDF，翻到的是一堆页码而不是答案。

GitHub 上有一个方案专门解决这个问题——book-to-skill：把整本书蒸馏成一个 Agent Skill，让你的智能体按需加载。这篇文章记录我从找仓库、装工具、蒸馏《重构（第 2 版）》中文版，到对比”女娲”人物 Skill、理顺 RAGFlow 知识库三层分工的全过程，包括一路踩的坑。

核心结论先放在这：书籍 Skill 是”知识工具书”，人物 Skill 是”决策风格模拟器”，两者不互斥，而是分工。

它把技术书籍 PDF（以及 EPUB/DOCX/Markdown/HTML/RTF/MOBI）提炼为统一的 Agent Skill。README 里最吸引我的一句话：

（回答问题时的 token 消耗，比把整本书塞进上下文少 24~51 倍）

为什么需要它

书读完就忘的问题，常规解法都不完美：

解法 问题
搜索 PDF 得到的是页码列表，不是答案
让 AI 讲这本书 要么幻觉，要么说没读过

book-to-skill 把书变成结构化 Skill，让智能体按需加载，这是第四个解法。

二、Codex 能不能装？

第一反应是”这仓库面向 Claude Code，Codex 能用吗”？结论是可以，但要看产物结构：

  • 它产出的核心是标准的 SKILL.md 技能目录
  • Codex 也支持这种结构：全局 ~/.codex/skills/<skill-name>/ 或项目内 .codex/skills/<skill-name>/
  • 若生成内容含 claude 命令、Claude 专用工具名或配置字段，需改为 Codex 对应方式；纯知识型的 SKILL.md 通常可直接用

三、关键对比：book-to-skill vs 女娲（人物蒸馏）

女娲是什么

alchaincyf/nuwa-skill（女娲.skill）是人物蒸馏工具：把芒格、巴菲特这类人蒸馏成 Skill。核心逻辑是”六路并行调研”，只有满足三个条件才收录为人物模型：

  1. 一个观点跨领域出现
  2. 能对新问题产生可检验推断
  3. 具有人物区分度

仓库里已有现成的 munger-perspective（芒格视角）。

核心差别：知识工具书 vs 决策风格模拟器

维度 书籍蒸馏 Skill 人物蒸馏 Skill
来源 一本或多本指定书籍 书、致股东信、演讲、访谈、历史决策与公开档案
目标 快速检索和应用书中方法 在明确证据范围内，按该人物的思考框架分析问题
输出 概念、清单、公式、章节结论、引用 原则排序、提问方式、决策流程、反例与”不做什么”
边界 只代表作者在书中的表达 不能宣称是本人或预测其真实决定，缺证据时必须说明
回答方式 “这份资料具体说了什么？” “这个人可能怎样拆解和判断这个问题？”
核心风险 漏掉章节或抽取失真 把公开形象、他人解读或旧观点误当成本人稳定信念

一个直观的例子

  • “把《穷查理宝典》蒸馏成 Skill” → 得到多元思维模型、反向思考、能力圈等可查可用的知识库
  • “把芒格蒸馏成 Skill” → 还要整合他跨几十年的公开表达、投资案例和否决逻辑，形成”芒格式决策框架”：先找激励错配、避免愚蠢、优先长期复利
  • “把巴菲特蒸馏成 Skill” → 重点变成企业质量、护城河、资本配置、管理层与估值纪律，而不只是复述某本书的段落

对巴菲特/芒格的最佳组合

不是二选一，而是两层叠加：

“蒸馏他们的书”得到的是可追溯的观点资料库；”蒸馏他们的人”得到的是有约束的分析角色——面对一家公司先看护城河、管理层、资本配置与估值；芒格则更强调激励机制、多元模型和反向排除。后者不能说”巴菲特一定会买/卖”，更不能包装成投资预测。

四、顺带对比：cangjie-skill（仓颉）

后来我还发现了一个同类的 Yeadon8888/cangjie-skill，它和女娲一样是”人物思维蒸馏器”，不是”书籍转 Skill 的工具”：

维度 book-to-skill cangjie-skill
蒸馏对象 一本书、文档夹、论文集合 一个人的公开认知上下文
输入重点 原书的章节、概念、方法、代码与表格 著作、访谈、决策、失败、时间线、矛盾
产物 可检索的知识与操作参考 Skill “某人视角”的思维 Skill
典型提问 “这段代码适合哪种重构手法？” “芒格会先质疑这项决策的什么前提？”
主要风险 压缩后遗漏、误解书中细节 把有限公开材料推断成真实人格或确定结论

共同限制也要看清：两者都不能自动证明提炼内容正确。 book-to-skill 的测试主要证明文本抽取和安全扫描能工作；仓颉的 quality_check.py 主要检查输出是否有”失败/边界/思维习惯”等结构，不验证这些故事是否真实、推断是否成立。README 的盲评分数应当视为作者自己的评测，不是独立事实。

五、三层分工：RAGFlow 知识库 vs 书籍 Skill vs 人物 Skill

那它们和 RAGFlow 知识库又是什么关系？答案是可以互补，默认不互斥——它们处理同一套资料的不同层次：

层 适合承担的职责 最适合的问题
RAGFlow 知识库 保存原始资料，按需检索、引用和持续更新 “1987 年巴菲特信里对某问题的原话和上下文是什么？”
书籍 Skill 将一本反复使用的书编译成结构化操作知识 “按《证券分析》的框架，核对这家公司缺哪些信息？”
女娲人物 Skill 提供有边界的认知框架与决策顺序 “用芒格的逆向思考，先排除这项投资的哪些风险？”

三种机制的本质区别

  • **RAGFlow 的核心是”检索”**：原书切块、建索引，提问时临时找相关段落，再由模型组织答案。适合资料量大、经常更新、需要回到原文核验的场景。
  • 书籍 Skill 的核心是”编译”：预先把章节、概念、模式、速查规则组织好，使用时按主题加载少量已提炼内容。适合稳定、常用、需落实到行动的问题。代价是压缩原著——新版本或遗漏内容需要重新蒸馏。
  • **人物 Skill 是”推理约束”**：不负责保存完整事实，而是规定优先看什么、如何判断、哪些事不做、何时承认不确定性。

什么时候会”打架”

真正冲突有三种情况：

  1. 人物口吻压过原文证据
  2. 书籍 Skill 版本过旧却仍当作事实
  3. RAG 检索片段被误当作完整观点

解决办法是规定优先级：原始资料/RAG 证据优先，书籍 Skill 次之，人物 Skill 只能解释和提出检查项。

六、实战：蒸馏《重构（第 2 版）》中文版

选源：为什么用 GitHub 中文仓库

我没有直接丢 PDF，而是选了 gausszhou/refactoring2-zh——《重构（第 2 版）》的中文 Markdown 版，12 个章节、声明 MIT 许可。优点：Markdown 源抽取质量远高于扫描 PDF，且许可证清晰。

安装踩坑 1：Python 证书链拦截

安装器默认走 ZIP 下载，被本机 Python 的证书链拦住了。Git 方式在本机可正常校验证书，改用安装器提供的 Git 回退路径继续安装。

安装踩坑 2：嵌套目录导致脚本路径缺失

安装完成后发现：安装器从仓库根目录安装时默认只取了顶层文件，scripts/、book_to_skill/、tools/ 这些可执行目录没进来，导致提取脚本路径不存在。修复：从同一固定提交把必需的三个目录补进本地安装，不改变其余内容。

抽取与生成

设计原则：主文件只放执行流程与选择规则，详细重构手法按章节拆到按需加载的参考文件，保留章节级来源定位——这样不会把整本书塞进上下文。

独立前测：不只看结构，还看输出质量

装完不是直接宣布成功，而是用一段隔离的遗留代码做前测。结果符合预期：

  • 识别出重复计算与嵌套条件两个坏味道
  • 没有过度建议多态化（对简单分支坚持最小改动）
  • 明确指出测试和调用点证据缺失——很克制，不瞎指挥

这个”克制”太重要了：一个重构 Skill 如果动不动就建议引入设计模式，反而会毁掉代码库。

八、什么时候该蒸馏书

天然适合的场景

一句话：你会反复把这本书当作”做事方法”，而不只是偶尔查一句原文。

场景 书籍 Skill 的作用 例子
架构与技术决策 固化设计原则和取舍清单 DDIA、领域驱动设计、微服务设计
代码质量治理 改代码前后做一致性审查 重构、遗留代码、TDD
固定工作流程 把方法变成步骤、输入输出和验收线 需求分析、技术写作、代码评审

  • 只读一次的书
  • 主要靠文采、叙事或情绪体验的文学作品
  • 需要精确原文、页码或完整上下文的资料
  • 版本变化很快的 API 文档
  • 内容太宽泛，无法转化为具体判断或行动

九、开发中要不要”先蒸馏书再写代码”？

不建议把”写代码”默认变成”先蒸馏一本书”。书籍 Skill 更适合做架构顾问、评审清单和工作方法，而不是代码生成器。

适合用书 Skill 的开发场景：

  • 反复遇到同类决策（分布式、数据库设计、重构、测试策略、领域建模）
  • 书中知识相对稳定（DDIA、Refactoring、Working Effectively with Legacy Code）
  • 希望每次开发都按一套明确原则审查，而不是模型临场发挥
  • 团队要复用同一套规范

不适合：

  • 只写一次小功能——直接看现有代码、测试和官方文档更快
  • 框架/API 更新快——官方文档比书籍 Skill 更可靠
  • 需要遵守本项目惯例——优先读 AGENTS.md、现有模块和测试

十、版权教训：找十本书蒸馏全踩空

需求：十本书做一个 /core Skill

想做一个集大成的 /core：第一性原理、系统思维、概率决策、认知偏差、人际影响、沟通、商业、学习系统、风险管理、长期主义（含《系统之美》《随机漫步的傻瓜》《思考，快与慢》《影响力》《非暴力沟通》《精益创业》《刻意练习》《反脆弱》《有限与无限的游戏》）。

踩坑：GitHub 上”有仓库” ≠ “有可合法蒸馏的原书”

逐本核验后发现关键事实：**GitHub 上确实有基于这些书的笔记/Skill 仓库，但几乎没有一本是”完整原书 + 授权可再利用”**。找到的往往是：

  • 二次蒸馏成果（getagentseal/founder-playbook、wondelai/skills），不能回溯成原书全文
  • 无许可证的课程转录、书单、笔记
  • 部分 MIT 二次 Skill（可复用但非原书）：cc-thinking-skills（第一性原理/系统思维/概率思考）、book2skills（芒格心智模型）、wondelai/skills（《影响力》《精益创业》）、ayi-nonviolent-communication（NVC）、model-thinking

《刻意练习》《有限与无限的游戏》甚至找不到任何可用的开源版本。

核心认知

仓库写 MIT，只能授权仓库作者自己的 Skill/代码，不能自动授权其中引用的出版社书籍。

最终选择：不生成”十本原书完整蒸馏版” /core，核验记录写进 [core-source-audit.md]，并明确区分”开源框架整合版”（用 MIT 二次 Skill）与”严格原书版”（需要你提供已购电子书或出版社授权来源）。宁可核验十次，不可误标一次。

总结

从找仓库到蒸馏《重构》中文版，再对比女娲与仓颉，这个项目的核心收获：

  1. 书籍 Skill = 知识编译器，人物 Skill = 人物认知提取器，前者给方法，后者给视角，不互斥
  2. 三层分工：RAGFlow 管检索与原文，书籍 Skill 管编译与操作清单，人物 Skill 管推理顺序与反模式
  3. 克制比聪明更重要：好的 Skill 会明确”证据不足就不建议”，不会为了展示能力而过度设计
  4. 安装踩坑都是环境问题：证书链拦截、嵌套目录、符号链接被安全扫描拒绝——每个都有明确解法，不要硬绕
  5. 版权是底线：GitHub 有仓库 ≠ 有可合法蒸馏的原书，二次 Skill 不能冒充原书蒸馏
  6. 验证要独立：结构校验之外，必须用真实任务前测输出质量，别把”生成了”当”生成了好的”

一个稳定的 Skill，不在于装了多少，而在于每次调用都能给出可核对、可执行、知道边界的答案。
