手机远程用 Agent：Tailscale 之后，我换了 Agents Anywhere

2026-11-184 分钟阅读更新于 2026-11-18

用 Tailscale 远程用 Hermes，每次都得保证手机和电脑都开着、VPN 都连着，折腾下来还不如一个免费远程桌面。后来换成 DSH 当执行载体、Agents Anywhere 当控制面，这篇写清中间的过程、和 UU 远程的正面比较，以及踩到的坑

前言

先说结论，省得看到最后才发现不是你想找的东西。

我一开始是用 Tailscale 远程用 Hermes 的。电脑开着，手机 VPN 开着，浏览器连上去，能用。但这套东西用久了就很烦：两个开关都得记得，少一个就白搭。

烦到什么程度呢，有次在地铁上想催一个 Agent 干活，摸出手机才想起来 Tailscale 没开。开完 VPN、重新连、等证书、找页面，前后两三分钟，等进去了，想干的那件事已经不想干了。

再后来我认真比了一下：如果只是「用手机操作电脑上跑着的东西」，装个网易 UU 远程不就完了，还免费，还不用配这配那。

这个念头当时挺打击人的。我自己拼出来的方案，还不如一个装了就用的远控软件。

但最后我没用 UU，也没把 Tailscale 删掉。中间换了执行载体（Hermes → DSH），又把远程方案换成了 Agents Anywhere。这篇文章就是讲中间这些事。

一、最开始：Tailscale 把手机接进跑 Hermes 的机器

1.1 为什么 Hermes 需要一个远程入口

Hermes 是我花三个月搭的金融研究智能体，搭建过程在这篇。一条深度流水线，跑在我自己机器上，每天扫新闻、更新公司档案、写复盘。

它的产出是定时的，但我看东西是随时看的。日报早上八点生成，我经常在通勤路上才翻。翻完基本会想干两件事之一：

  • 「这条不对，让它重新核下来源」
  • 「这家公司加进 watchlist，明天开始盯」

在电脑前这是两秒钟的事。人不在电脑前就变成「晚上回去再说」，而金融信息晚上再说往往就没意义了。

所以我需要的第一件事很朴素：在外面能碰到家里那台机器。

1.2 为什么选 Tailscale

当时能选的有这么几个，我最后选 Tailscale 主要图安全，不是图方便。

方案 代价
路由器端口映射 + 公网 IP 服务直接挂公网，认证做薄一点就出事故
内网穿透（frp 之类） 还得有台公网 IP 的中转机，暴露面没变小
Cloudflare Tunnel 好用，但流量出自己家、要绑域名
Tailscale 节点直连，不出公网、不绑域名、不开端口

Tailscale 底下是 WireGuard。设备加进同一个 tailnet，各自拿到 100.x.y.z 的地址，能打通就直连，打不通才走 DERP 中继。对我有用的就三点：不开放公网端口、有身份和 ACL、有 MagicDNS（手机上是 http://mac-mini:4001，不用记 IP）。

免费额度个人够用，这块没什么好纠结的。

Hermes 那边只动了三个地方。

手机上装客户端、登同一个账号、开 VPN 开关，浏览器访问 https://mac-mini.<tailnet>.ts.net 就进去了。

这一套配下来不到十分钟，也没出过什么事。

1.4 但是用起来别扭

问题不出在故障上。整整一段时间它都挺稳的，我没碰到过连不上之类的事故。

问题是每天都要做的两件小事。

第一件，它要求两样东西同时开着。电脑要开着，手机 VPN 也要开着。单看都不苛刻，叠一起就是负担。手机那个 VPN 开关我经常是想用的时候才想起来没开，开了之后又是一次连接、一次等待。等连上，兴致已经过了。

第二件就有点打击人了。我某天在心里过了一遍：用手机操作电脑上跑着的东西，最省事的办法是什么？

答案是手机上已经装着的那个东西。网易 UU 远程，免费，Windows/macOS/iOS/Android 都有，连上去就是我那台电脑的真实桌面。想点什么点什么，想开什么开什么，不用管 tailnet，也不用管什么 Web 入口。

所以不是 Tailscale 不好，是我拿它当了别的东西在用。

二、拆开看，远程用 Agent 缺的到底是什么

第二阶段开始时我没急着找新工具，先把这个事拆了一下。拆完发现选型没什么好纠结的。

2.1 四件事，不是一件

远程用 Agent，要解决的问题其实是四层：

层 要解决什么 做不好会怎样
网络可达 手机能不能连到工作机 连不上、超时、DNS 不解析
会话状态 连上之后看到的还是那个会话吗 重载丢上下文、历史对不上、多端各说各话
交互请求 Agent 中途要审批时我能收到吗 弹窗没人看见、任务卡到超时
工作区操作 我能看文件、看 diff、开终端吗 只能看文字输出，改不了也验证不了

这四层是递进的，但互相替代不了。网络通了不代表会话能续上，会话能续上不代表审批能推到你手机上。

2.2 Tailscale 只管第一层

它做得其实很干净。第三层网络的组网工具，保证包能到，别的不管，也不该管。

问题出在我的期待上。我当时想的是「网络通了，剩下的浏览器会解决」。这句话在桌面上成立，在手机上不成立：手机上的浏览器不是应用，是个随时会被系统挂起、切走、回收的进程。

2.3 手机不是缩小的桌面

这条我踩得最实。

我在手机上用 Hermes 的 Web 页面干过三件事，三件都别扭。

审批弹窗。 Agent 跑到一半要问我「这个来源算不算一手信源」。桌面上那是侧边栏一个按钮，手机上是一个需要精确点击的区域，而且我大概率正在别的 app 里。等我想起来切回去，任务已经按超时策略走了默认分支。

长输出。 一份深度报告在手机上就是一条很长的滚动条。滑动没问题，问题是我需要一边看一边指，「第三段这个结论的依据在哪」。桌面能并排放，手机只能来回跳。

断线重连。 手机锁屏、切网、进电梯，断线是常态。桌面版网页的处理方式是重连后重新拉一次数据，这在手机上意味着滚动位置、展开状态、输入框里没发出去的字，全丢。

这三件事没有一件是 Tailscale 的错，也没有一件是换个更好的隧道能解决的。它们在第 2、3 层。

2.4 那为什么不用远程桌面

这是我给自己提的最较真的一个问题，也是最容易一句话糊过去的：远程桌面能看到真桌面，想点哪里点哪里，还免费，为什么还要另外找东西？

它对的地方我得承认。在「用手机操作电脑」这件事上，它的成熟度比我自己拼的那套高得多：

  • 看到的是真实桌面，不用为每个工具单独做移动端适配
  • 任何软件都能操作，不受「这个工具有没有 Web 版」的限制
  • 免费，装了就可用，不用配 tailnet、不用管 ACL、不用签证书
  • 桌面端交互逻辑原样保留，不会出现按钮在手机上点不到

所以 1.4 里那句「还不如一个免费远控软件」是字面意思。

但它解决的是另一类问题。摆一起看会比较清楚：

远程桌面 Agents Anywhere
传的东西 像素（视频流） 会话对象（消息、时间线、审批、文件）
交互对象 一个 1920×1080 的桌面 为手机重排的会话界面
带宽 持续视频流，随画面波动 文本和结构化数据，间断、量小
等的时候 手机被画面占住 可以退出，需要你时再叫你
中途审批 你得正好在看着 是条待办，会等你
断线恢复 重连、重新同步画面 会话在服务端，接着看

远程桌面传的是像素。Agents Anywhere 传的是语义。

打开个软件随便看看，这个差别无所谓，甚至远程桌面更强，因为通吃。但 Agent 跑三分钟要你拍板一次的时候，语义层的优势就很实在了。

画面流没法告诉你「有两件事在等你决定」。它只能显示屏幕现在长什么样。那个审批弹窗要是被别的窗口盖住了，或者你根本没在看，它就是不存在的。

再算两个现实账。

带宽上，远程桌面是持续视频流，地铁里信号一抖画面就糊成马赛克。Agent 的输出是文字，几百 KB 的量级，弱网下只是慢，不会不可用。

占用上，用远程桌面时手机屏幕是被占住的，没法一边挂着一边干别的。而 Agent 这类东西的特点是跑很久、只在少数时刻需要你。

2.5 所以我要的是个什么东西

把上面两层合起来，需求就具体了：一个能把会话、审批、文件、终端都端到手机上的控制面，执行还留在我的机器上。

拆成三条，缺一条都不成立。

执行必须在本地。工作区、密钥、登录好的模型账号都在那台机器上，搬到云端等于全部重来。

交互必须是移动原生的。不是把桌面缩小，是按手机的方式重新组织。

状态必须持久。会话在服务端，换设备、断线、锁屏都不丢。

远程桌面满足第一条，后两条不满足。Tailscale + Web 三条都不太满足。

三、中途先把 Hermes 换成 DSH

顺序上我是先换执行载体，再换远程方案。因为远程方案怎么选，取决于载体长什么样。

3.1 流水线和运行时不是一回事

Hermes DSH
形态 一条深度流水线 通用 Agent 运行时
擅长 把一件事做得很专业 承接各种不同类型的活
会话 单方向、任务式 多会话、可并行、可长期存在
扩展 改代码 装插件、写 Skill、配小队

Hermes 只服务金融研究这一件事，而我日常要用的 Agent 远不止金融：写代码、写文章、查资料、跑脚本、审 diff。

之前那篇 ds-bot 的记录里写过这个转变：一堆事压在一个会话里，第三天基本就被挤没了。DSH 的解法是把事拆给多个长期存在的 Session，每个有自己的角色、模型和权限。

Hermes 没有消失，位置反而更清楚了。金融研究那条流水线继续留在 Hermes 里，它的规则（口径统一、数字可追溯、档案只追加）是专门化的，套到别的事上就是牛刀杀鸡。通用场景全搬到 DSH。

3.2 这个差别在手机上会被放大

这点是我换完之后才意识到的，但它可能是最关键的一条。

流水线的交互是稀疏的。给个任务，等结果，看报告。中间可能十几次工具调用，需要我介入的只有开头和结尾。这种形态在手机上勉强能忍，打开看一眼关掉就行。

运行时的交互是稠密的。跑一个任务，中途可能问三个问题、要两次审批、报一次失败让你决定重试还是换路。每一环都要切回浏览器、滚动、点。这就不是可用性的问题了，是根本不会去用。

人会给自己找理由说「能用就行」，实际行为是「能不用就不用」。

3.3 换完之后，新问题冒出来了

DSH 换好，能力问题解决了，形态问题原封不动。

我在电脑前开三个会话跑着，出门，然后什么都干不了。会话还在跑，进度看不到；跑到一半要我确认权限，我不知道；跑完了想追问，得等回家。

2.5 里列的那三条，DSH 把第一条坐实了。剩下两条，得靠别的东西补。

四、Agents Anywhere 接手控制面

4.1 先划清它不是什么

这类工具最容易被误解成又一个云端 Agent。不是。

它不是 AI Agent，也不是模型服务。它是一个跨设备的 Agent 工作台，连接你工作设备上已经在跑的 Codex、Claude Code、DeepSeek Harness，在桌面、手机、平板、Web 上查看会话、继续对话、回复请求、管理文件和终端。

任务还是在连接的工作设备上执行，用它自己的工作区、权限和已经登录好的模型账号。

开源，Apache-2.0，可以连官方 Cloud，也可以 Docker 自托管。

这两条对我挺关键。模型账号和费用都不变，它沿用工作设备上 Agent 的登录状态，不用额外买订阅。跟上一篇里「付不起 Grok Bot 订阅」是同一个思路，把已有的东西用起来，别再多开一份账单。

4.2 四块东西各自干什么

组件 跑在哪 干什么
客户端 我的设备 展示会话和时间线，发消息、做审批
Server Cloud 或自托管 登录验证、指令转发、会话与附件存储
Connector 工作设备 长连接 Server，把 RPC 落到本机执行
Runtime 工作设备 Agent 适配层，启动和驱动 Codex / Claude / DSH

这个分层刚好对上前面拆的那四层。网络转发归 Server，会话状态归 Server 加 Connector，交互请求走 RPC，工作区操作由 Connector 在本机提供。四层都有人负责，不用我自己拼。

4.3 它对上了哪些具体问题

我碰到的坑 它怎么处理
审批弹窗没人看见 审批和输入请求是一等对象，会出现在手机时间线上，等你处理
长会话滚动位置丢失 会话和 Timeline 在服务端持久化，换设备打开还是同一条线
想验证 Agent 说的对不对 能浏览预览文件、上传下载附件、开远程终端
多台机器 设备、项目、会话三级切换，同一账号下都能看到
必须守着那台电脑 手机负责控制，工作设备负责执行

第一条是我最看重的。Agent 停下来等人，是这类工具里最难缠的一种状态，因为它不报错、不失败，就那么挂着。

桌面端有侧边栏提醒你，移动端如果不把这件事做成主动推送的对象，这个功能等于不存在。

4.4 三个 Runtime 能力不一样

DSH、Codex、Claude Code 都能接，但能力并不完全一致。能不能选模型、能不能打断、能不能恢复会话、审批粒度多细，取决于各 Runtime 自己支持什么，最终以客户端显示为准。

我的感受是这样：

Runtime 我拿它干什么 手机上怎么样
DSH 主力，长会话、多任务、写作和研究 接入最完整，官方专门做了桥接插件
Codex 单点代码任务，跑完就结束 审批流清晰，适合扔个任务然后走开
Claude Code 大仓库里的改动，需要看 diff 看 diff 和文件比纯聊天界面舒服

用法上我就一条原则：需要我在手机上频繁介入的活，交给接入能力最完整的那个。一次性的、不需要中途审批的，哪个顺手用哪个。

5.2 登录，连上工作设备

装完重启 DSH，左侧边栏进「远程控制」。

先选服务，Agents Anywhere Cloud 或者填自己部署的地址。然后在系统浏览器里完成登录授权。等设备显示在线，确认 DSH Runtime 可用，选工作目录，建会话，发第一个任务。

有个容易搞混的地方：Agents Anywhere Desktop 和 DSH Desktop 是两个不同的应用。如果插件检测到 Agents Anywhere Desktop 正在跑，会引导你去那个应用继续设置，避免两个应用同时管同一台机器。这不是报错。

5.3 自托管的话

Cloud 的服务器在国内，访问体验更好。但我还是自己部署了一遍，理由一是想知道数据落在哪，二是本来就有现成的机器。

到这儿 Tailscale 又回来了。自托管 Server 如果只在家里那台机器上，出门怎么访问？别给它开公网端口，用 Tailscale 在 tailnet 内暴露就行：

这也是前面那句「Tailscale 没被删掉」的来由。它从方案变成了基础设施，以前它是全部，现在只负责把自托管 Server 安全地送到手机面前。

六、Codex 和 Claude Code 怎么接

6.1 一台机器挂多个 Runtime

Connector 在设备详情里可以添加多个 Agent，装了哪个就能接哪个。前提是工作设备上已经装好并登录过对应的官方 CLI。Agents Anywhere 不管模型账号的事，它只负责驱动这些 CLI。

顺序是先在工作设备上把 Codex / Claude Code 装好登好、能正常跑，然后在 AA 的设备详情里添加，最后新建会话时选「哪个设备 + 哪个 Agent」。

6.2 找不到命令就填绝对路径

第一次接 Codex 就撞上了。设备在线，Agent 也添加了，会话起不来。

原因是 Connector 有自己的 PATH。你在终端敲 codex 能跑，不代表 Connector 那个进程能找到它。用 Homebrew、nvm、asdf 这类会改 PATH 的方式装的 CLI，Connector 拿到的环境变量里可能根本没那些目录。

解法很土：在实例配置里填绝对路径。

这不是 AA 的问题，所有后台进程驱动 CLI 的工具都会碰见。

6.3 别让三个 Connector 抢一台设备

同一台机器上，有三个地方能启动 Connector：Agents Anywhere Desktop（内置）、anywhere-cli 命令行、DSH 的桥接插件。

给同一个系统用户只选一种启动方式。三个一起跑会互相抢同一台设备的连接，表现是设备一直在线但操作就是不对劲，而且日志分散在几个地方写，排查很难受。

我这边是主力机用 DSH 插件启动，因为主要在 DSH 里干活。偶尔要单独跑 Codex 会话，才去 Desktop 那边。

七、踩过的坑

7.1 设备在线不等于 Runtime 可用

界面上「设备在线」只说明 Connector 连上了 Server，跟 Agent 能不能跑是两件事。

排错顺序是：设备在线 → Runtime 状态 → 会话是否支持这个操作 → Connector 日志。跳过中间两步直接翻日志，会浪费很多时间在无关的报错上。

7.2 代理会吃掉上传速度

另外两个容易误解的：只设 NO_PROXY 不会关掉系统代理，它只决定哪些地址不走代理；还有不支持 PAC，用 PAC 脚本的网络在「跟随系统」下可能静默走直连，这种就得在「Connector 网络」里手动填地址。

7.3 版本错位，表现是不报错

这条最容易让人卡住，因为它的表现是什么都不报，就是一直等待。

规则是：升级 Agents Anywhere Desktop 或 Connector 的 MINOR 版本（比如 2.0.x → 2.1.0）时，桥接插件要一起升。不然本机连接会一直停在等待状态。

插件本身还有个 DSH 版本兼容范围，写在它自己那份 peerDependencies 里（我装的时候是 DSH >=0.2.0-rc.1 <0.3.0-0，开发基线 0.2.2-rc.4）。

不满足时不要加版本豁免。豁免只是绕过检查，运行时该崩还是崩。要么升 DSH，要么换个兼容的插件版本。

还有个细节：通过「插件」页面装的插件暂时不会自动更新，升级要先卸载再装。

7.4 别指望无人值守

这条不算坑，是个得先接受的前提，我自己一开始就想错了。

手机负责控制，工作设备负责执行。所以远程用的前提是那台机器开着机、连着网、Connector 在跑、对应 Runtime 正常。

macOS 上尤其注意：机器睡眠等于 Connector 掉线等于手机端什么都做不了。我是把「接电源时不睡眠」设成了常态，否则这套东西只在我坐在电脑前的时候可用，那就毫无意义了。

Windows 上的对应行为是关窗口会隐藏到托盘，Connector 继续跑，从托盘退出才是真停。

7.5 数据落在哪得自己清楚

Agent 在工作设备上执行，用的是那台机器的工作区和终端权限。但会话内容、Timeline、上传的附件，会经过或存储在 Server 上。

用 Cloud 就是存在官方服务器，自托管就是存在你自己部署的实例里。这不是谁的问题，是这类产品绕不开的结构：手机要看到会话，会话就得放在手机拿得到的地方。

我的处理很简单，涉及真实账户、密钥、个人资料的活不从远程端发起。远程端我只用来推进读、判断、调度这类工作。

7.6 升级卸载的两件事

卸载插件不会删数据。账号、设备连接、设置都在 ~/.agents-anywhere/dsh-bridge-next/，重装后接着用。想彻底清掉得先在插件的「设置 → 维护」里执行「恢复出厂设置」再卸载。

内置插件不要叠加 npm 安装。DSH Desktop 内置的那份和它自己的版本配套，版本号带 -desktop 后缀，跟 npm 上那个包不是同一个构建。硬装一份上去，遇到的现象会很难解释。

八、现在怎么分工

场景 走哪条路
在电脑前长时间干活 直接开 DSH Desktop，不走远程
通勤路上看进度、催一句、追个问题 手机 → Agents Anywhere → DSH
在外面碰到 Agent 停下来等审批 手机处理，这一格用得最多
只想跑个代码任务，跑完就走 手机 → Codex
要看 diff、翻文件、开终端 手机 → Claude Code 或 DSH 的文件和终端面板
彻底连不上要救火 Tailscale + SSH

8.1 Tailscale 还留着干什么

不是为了情怀，是它还有三个位置。

一是兜底。Agents Anywhere 整条链路（客户端 → Server → Connector）任何一环出问题，SSH 还在，这是不依赖任何第三方服务的最后一条路。

二是给自托管 Server 留个安全入口。前面说的，不开公网端口，用 tailnet 内的 HTTPS。

三是管 Server 本身。数据库、备份、日志、升级，这些本来就需要个稳定的远程入口，而这正是 Tailscale 最擅长的事。

8.2 什么情况下别上这套

也有几种情况我建议用简单方案就行。

只用一种 Agent、任务稀疏、几乎不需要中途介入的，Tailscale + Web 够了，不用再叠一层。

工作设备不是常开的，这套会持续给你「设备不在线」的挫败感，收益是负的。

对数据经过第三方极度敏感又不想自托管的，这套不合适，回到纯内网方案去。

只是想看结果不想推进任务的，把结果推到 IM 更省事。

最后

回头看这件事，被改变的其实是两个判断。

一个是关于「够得着」的。以前我以为远程使用的难点在网络，把包送到目的地就完事了。后来才发现，包送到了只是开始。

另一个是关于「自己拼」的。我花时间配 tailnet、签证书、写 ACL，做出来的东西还不如一个免费 App 顺手。这件事不太好受，但它至少说明了一件事：这个位置本来就该有专门的产品，而不是我自己拼。

如果你也在折腾类似的事，可以先问自己一个很土的问题：你为了「用一下」，需要先做几步准备？如果需要三步以上，那大概就是用不起来的。
