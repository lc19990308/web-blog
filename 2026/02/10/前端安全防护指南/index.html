前端安全防护指南：XSS、CSRF 与 HTTPS

2026-02-104 分钟阅读更新于 2026-08-10

前端安全的重点是正确处理不可信内容、配合服务端会话策略并限制浏览器能力。本文覆盖 XSS、CSRF、CSP、Cookie 和安全响应头的真实边界。

前端不能替服务端做安全决策

前端校验能让用户更早看到错误，却不能阻止攻击者绕开界面直接调用接口。权限判断、数据校验、Cookie 属性和响应头必须由服务端执行；前端的责任是避免把不可信数据变成可执行内容，并按约定安全地发起请求。

先把边界记住：用户输入、富文本、URL 参数、接口响应和第三方脚本都应当作不可信来源。只要其中任何一项进入 HTML、JavaScript URL 或敏感操作，就需要明确的处理规则。

净化不是一次性配置。富文本组件升级、允许的链接协议和图片来源变化后，都要重新检查策略。涉及评论、运营编辑器或 Markdown 渲染时，服务端也要在保存或输出的边界重复执行校验。

CSP 是第二道防线

Content Security Policy 不能弥补不安全的 v-html，但能在注入发生时限制脚本加载和执行范围。应在 HTTP 响应头中设置它；meta 形式有能力限制，不能替代完整的服务端策略。

CSRF：取决于认证方式

CSRF 主要影响浏览器会自动携带认证 Cookie 的站点。SameSite 能降低跨站携带 Cookie 的机会，但不能替代服务端对敏感写操作的验证。选择 Lax、Strict 或 None; Secure 前，要先确认登录跳转、嵌入页面和跨站支付回跳等真实流程。

Token 的生成、绑定和校验在服务端完成。前端只从受控页面读取它并随请求发送，不能把“请求带了 token”误认为已经得到授权。

__Host- 前缀要求 Secure、Path=/，且不能设置 Domain，能减少子域覆盖 Cookie 的风险。是否使用 Cookie、内存令牌或其他认证模型，取决于威胁模型和产品流程；把令牌放进 localStorage 会在 XSS 成功时扩大泄露面，并不是通用默认方案。

HTTPS 应覆盖所有页面和静态资源。不要在 HTTPS 页面加载 HTTP 资源，也不要用协议相对 URL 掩盖配置问题。确认全站 HTTPS 后，再由服务端启用 HSTS；预加载或 includeSubDomains 是难以回退的决策，必须评估所有子域。

响应头需要按场景组合

以下响应头由服务端或 CDN 配置。它们不是一段可复制到所有项目的模板：

响应头 解决的问题 注意点
Content-Security-Policy 限制脚本、嵌入和资源来源 先用 Report-Only 验证
X-Content-Type-Options: nosniff 防止 MIME 嗅探 通常可直接启用
Referrer-Policy 减少 URL 中的来源信息泄露 评估分析与支付回跳
Permissions-Policy 收紧摄像头、定位等能力 按页面实际需要授权
Strict-Transport-Security 强制后续 HTTPS 访问 只在全站 HTTPS 后启用

frame-ancestors 是防点击劫持的现代 CSP 指令。旧的 X-Frame-Options 仍可作为兼容补充，但不能通过 <meta> 标签可靠地配置。不要再加入 X-XSS-Protection，现代浏览器通常忽略它，部分旧实现还可能引入意外行为。

发布前检查

  • 搜索 v-html、innerHTML 和动态 URL，逐个确认数据来源和净化策略。
  • 用浏览器开发者工具检查真实响应头与 Cookie 属性，而不是只看配置仓库。
  • 对写操作测试跨站表单、缺失 CSRF Token 和错误 Origin，确认服务端拒绝它们。
  • 在 CSP Report-Only 阶段收集并处理违规，确认第三方脚本有明确所有者。
  • 检查打包后的前端环境变量，确保 API 密钥、私钥和服务端令牌没有进入浏览器。

安全不是在页面末尾补一段代码。把信任边界、会话策略和发布检查写进开发流程，能比一张“安全头速查表”更早发现问题。
